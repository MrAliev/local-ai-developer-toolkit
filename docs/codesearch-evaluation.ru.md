## Команды и сырые артефакты

### Воспроизводимый способ

Запускайте закоммиченный evaluator из канонической неизменяемой установки, в которой
`codesearch` и `LocalAi.Broker.dll` относятся к одной опубликованной feature-сборке.
Если активна другая неизменяемая версия, после подтверждения простоя брокера следуйте
описанному в README workflow публикации и
`localai-launcher activate <version> --stop-running`; не заменяйте DLL на месте. Все
запросы по-прежнему идут через общий брокер, а не напрямую в Ollama.

Следующий синтаксис задан закоммиченным usage `CodeSearch.Cli` и передачей аргументов
launcher:

```powershell
$launcher = 'C:\Users\Mr.Aliev\tools\LocalAi\bin\launcher\localai-launcher.exe'
$cases = (Resolve-Path 'tests\CodeSearch.Tests\Fixtures\SearchEvaluation\cases.json').Path
$repo = 'C:\Users\Mr.Aliev\tools\LocalAi'

& $launcher run codesearch evaluate --cases $cases --root $repo --profile |
  Set-Content -Encoding utf8NoBOM -LiteralPath (Join-Path $env:TEMP 'codesearch-eval-profile-cold.json')
& $launcher run codesearch evaluate --cases $cases --root $repo --profile |
  Set-Content -Encoding utf8NoBOM -LiteralPath (Join-Path $env:TEMP 'codesearch-eval-profile-warm.json')

& $launcher run codesearch evaluate --cases $cases --root $repo --no-floor |
  Set-Content -Encoding utf8NoBOM -LiteralPath (Join-Path $env:TEMP 'codesearch-eval-no-floor-cold.json')
& $launcher run codesearch evaluate --cases $cases --root $repo --no-floor |
  Set-Content -Encoding utf8NoBOM -LiteralPath (Join-Path $env:TEMP 'codesearch-eval-no-floor-warm.json')
```

Для настоящей пары cold/warm сначала дождитесь, пока поддерживаемая idle-политика
брокера увидит отсутствие queued и running работы в течение 30 минут и выгрузит
резидентную модель эмбеддингов. Подтвердите состояние MCP-инструментом
`local_models_status`. Один раз выполните первую команду, а сразу после неё — вторую.
Перед парой без порога снова дождитесь и подтвердите управляемую брокером idle-выгрузку,
затем также выполните две команды подряд. Если модель уже была резидентной, пометьте
первый результат как тёплый, а не холодный. Не используйте прямые команды Ollama для
проверки, загрузки или выгрузки модели.

реализация evaluator находилась на `b4c621d`. В issue #6 отслеживается привязка к пути
сборки, из-за которой клиент из worktree не принимает уже запущенный брокер.
Установленная версия не заменялась и не перезапускалась. Игнорируемый временный adapter

`SearchService` -> `BrokerEmbeddingClient` -> общая устойчивая очередь.

восстановило каждый snippet из неизменяемого Git-коммита с теми же границами, что и

оставлены без изменений. Эта детерминированная трансформация не запрашивала эмбеддинги
и не меняла исходные наблюдения качества, числа символов или времени.

## Измеренные факты

Метрики качества и объёма результатов совпали между двумя запусками каждого режима.
Поэтому для детерминированных метрик в таблице можно использовать любой запуск, а
время приведено отдельно.

`Строки исходников` учитывают строки исходного текста, фактически присутствующие в
возвращённых snippet, включая пустые строки исходника. Синтетическое многоточие
усечения исключено, а синтетическая диагностика недоступного snippet считается как
ноль строк.

| Метрика | Без порога, запуски 1/2 | Профиль, холодный/тёплый | Изменение |
|---|---:|---:|---:|
| Precision@5 | 0.133333 | 0.133333 | 0 |
| Recall@10 | 0.777778 | 0.777778 | 0 |
| Средний ранг первого релевантного результата | 4.388889 | 4.388889 | 0 |
| False positive для no-answer | 6/6 (доля 1.0) | 6/6 (доля 1.0) | 0 |
| Символы ответа | 151 071 | 147 651 | -3 420 (-2.26%) |
| Строки исходников | 2 517 | 2 499 | -18 (-0.72%) |
| Чтения чанков | 240 | 238 | -2 (-0.83%) |
| Сумма чтений различных файлов по случаям | 156 | 152 | -4 (-2.56%) |

| Запуск | Время evaluator |
|---|---:|
| Профиль, холодный | 72 246.5 мс |
| Профиль, тёплый | 71 308.5 мс |
| Без порога, тёплый запуск 1 | 67 625.1 мс |
| Без порога, тёплый запуск 2 | 68 556.8 мс |

Холодный запуск профиля был на 938.0 мс медленнее его тёплого повтора. Тёплый запуск
профиля был на 3 217.6 мс (4.73%) медленнее медианы двух тёплых запусков без порога.
При одной паре cold/warm и обычном шуме планировщика общего брокера это наблюдение
времени, а не доказательство того, что порог вызывает регрессию задержки.

Не изменились четыре пропуска ответов:
`intent-runtime-acl`, `text-vector-route`, `text-shared-fifo` и
`text-russian-install`. Всего порог удалил два возвращённых чанка. В случае
`none-email-reset` число результатов снизилось с 10 до 8, но случай остался false
positive, потому что кандидаты с положительным lexical score намеренно допускаются
даже при векторном score ниже порога.

## Нарезка по символам, измеренная на фронтенд-корпусе

Измерение выше — это сам репозиторий LocalAi: C#, который режется по символам с давних пор,
задолго до того, как это появилось для других языков. Показать эффект изменения он не может.
Этот раздел — то самое «до и после», прогнанное на корпусе, которого изменение действительно
касается.

**Корпус.** Приватный репозиторий на React/TypeScript: 2 653 проиндексированных файла, из них
1 713 `.ts` и 942 `.tsx`. Двенадцать кейсов на естественном языке, по-русски, у каждого один
ожидаемый файл и ни одного символа. Цели без символов — сознательно: цель с символом оценивала бы
новую форму чанка на корпусе, который такой формы дать не мог, и сравнение польстило бы само
себе.

Сами кейсы здесь не закоммичены: их пути принадлежат чужому репозиторию. Числа закоммичены —
именно этого и требовал критерий приёмки.

**Три индекса.** Формат чанков 1: поколение `ac83250b`, 3 471 чанк — везде окно по строкам.
Формат чанков 2: поколение `44cd3fb5`, 6 079 чанков — нарезка по телам, о которых сообщают
адаптеры. Формат чанков 3: поколение `84776c92`, 6 894 чанка — плюс нарезка по объявлениям,
которые адаптер называет, но тела для них не сообщает. Тот же репозиторий, тот же коммит, та же
модель эмбеддингов, те же двенадцать кейсов, по одному профильному прогону на каждый формат.

| Метрика | Формат 1 | Формат 2 | Формат 3 |
|---|---:|---:|---:|
| Precision@5 | 0.116667 | 0.116667 | 0.133333 |
| Recall@10 | 0.750000 | 0.750000 | 0.750000 |
| Средний ранг первого релевантного | 5.500000 | 4.916667 | 4.750000 |
| Символов в ответах | 70 245 | 66 087 | 63 281 |
| Строк исходника в выдаче | 1 426 | 1 282 | 1 204 |
| Прочитано чанков | 120 | 120 | 120 |
| Уникальных файлов на кейс, суммарно | 99 | 102 | 101 |

| Форма выдачи | Формат 1 | Формат 2 | Формат 3 |
|---|---:|---:|---:|
| Попаданий с именем символа, все файлы | 0 из 120 (0%) | 33 из 120 (28%) | 50 из 120 (42%) |
| Попаданий с именем символа, только `.ts`/`.tsx`/`.py` | 0 из 86 (0%) | 33 из 85 (39%) | 50 из 89 (56%) |
| Строк исходника в этих попаданиях | 3 819 | 2 232 | 2 186 |

**Как это честно читать.** Формат 2 не сдвинул ни precision, ни recall. На этом корпусе нужный
файл и так находился; изменилось то, что приходит вместе с ним: релевантное попадание встречается
примерно на полранга раньше, ответ на 5.9% короче по символам, а попадания в тех языках, которых
касается изменение, охватывают на 42% меньше строк исходника. Результат стал определением, а не
окном в шестьдесят строк, внутри которого определение случайно оказалось.

Формат 3 — первое из этих изменений, которое вообще сдвинуло precision: 0.117 → 0.133, то есть
одним релевантным попаданием в первой пятёрке больше на все двенадцать кейсов. Это одно
попадание на корпусе из двенадцати — направление, а не измеренный размер эффекта. Что здесь
действительно измерено, так это покрытие: в этих языках имя символа теперь несут 56% попаданий
вместо 39%, потому что компонент, объявленный как `export const X = memo(() => …)`, наконец
получил собственный чанк, — и ответ стал ещё на 4.2% короче по символам.

Пятьдесят шесть процентов, а не все, потому что для непокрытых участков окно по-прежнему верно:
импорты, код уровня модуля, промежутки между функциями и объявления, слишком мелкие или слишком
глубоко вложенные, чтобы резать по ним.

**Чего это стоит.** На формате 2 корпус вырос на 75%, с 3 471 чанка до 6 079: определение,
которое раньше делило окно с соседями, получило собственный вектор. На формате 3 — ещё на 13.4%,
до 6 894. На репозитории размером с IntelWash это тот самый час, названный в заметках релиза, и
случается он один раз на смену формата.

Время по часам между этими тремя прогонами несопоставимо и намеренно не сведено в таблицу.
Пересборки форматов 1 и 2 считали эмбеддинги со скоростью около 13.6 чанка/с; пересборка формата
3 шла на 10.3 (6 894 чанка за 671.1 с), потому что делила очередь брокера с базовой сборкой
другого репозитория, и то же соперничество видно в прогоне запросов (129.1 с против 101.0 с на
тех же двенадцати). Это занятость машины, а не медленность формата.

**Происхождение прогона на формате 3.** Измерено 2026-08-20 с ветки разработки, до того как
этот отчёт был закоммичен. Индекс собирался в одноразовый runtime root, а не в установку самой
машины: установленный клиент сохранил свой индекс формата 2, пока рядом мерили сборку, которую
он прочитать не может. Эмбеддинги всё равно шли по пути `SearchService` → `BrokerEmbeddingClient`
→ общий FIFO-брокер LocalAi, ни одного прямого запроса к Ollama не было. Размеры корпуса взяты из
самих сборок. Разделение чанков на именованные символом и оконные, а также строки исходника,
которые каждый вид покрывает, посчитаны игнорируемым локальным харнессом: он гоняет
закоммиченный чанкер по рабочему дереву, ничего не эмбеддя. На формате 2 имя символа несли 2 985
чанков из 6 079, на формате 3 — 3 966 из 6 894, а строк исходника `.ts`/`.tsx`/`.js`/`.jsx`/`.py`
внутри символьных чанков стало 67 527 вместо 53 668. Харнесс не является продуктовым путём
исполнения и не закоммичен.

**Поправка, найденная уже после этого прогона.** Работа над корпусом, который смог бы этот замер воспроизвести, вскрыла дефект в той самой границе, о которой абзац выше: выведенный участок забирал себе комментарий, документирующий объявление *ниже*, отчего проза попадала в чанк с чужим именем, а однострочное объявление вырастало настолько, чтобы получить чанк, которого не должно было получить. Перенарезка того же дерева с исправлением даёт 6 868 чанков вместо 6 894 и 3 936 именованных символом вместо 3 966 — тридцать объявлений на весь репозиторий. Прогон retrieval ради разницы в двадцать шесть чанков из семи тысяч не повторялся: таблица выше — это то, что дал измеренный индекс, и сказать об этом честнее, чем поставить число, которое никто не мерил.

## Корпус, который принадлежит этому репозиторию, и что им можно измерить

Замер на фронтенде выше не может повторить никто из читающих: его двенадцать кейсов называют пути
в репозитории, который этому проекту не принадлежит. `tests/Shared/SyntheticFrontendRepository.cs`
порождает тот, который принадлежит, — детерминированно, из закоммиченного кода, — а
`tests/CodeSearch.Tests/Fixtures/SearchEvaluation/synthetic-frontend-cases.json` задаёт ему 48
вопросов. Репозиторий — небольшой фронтенд: общие модули с разными задачами и сколько угодно
папок-фич, написанных по одному набору шаблонов.

**Что он измеряет в CI, на каждом pull request.** Форму нарезки, для которой модель не нужна.
Сгенерированное дерево индексируется настоящим `scip-typescript` и режется настоящим чанкером, а
инварианты, которые были прозой в `SymbolAwareChunker`, становятся проверками: объявление,
инициализированное вызовом, получает чанк; свойства объектного литерала — нет; однострочное
объявление остаётся на окне; каждая строка исходника попадает ровно в один чанк; каждый символ,
названный корпусом, существует. Это и есть то «до и после», которое имеет смысл для изменений
нарезки, — и своё место корпус оправдал сразу: первый же прогон нашёл, что выведенный участок
забирает комментарий, документирующий следующее объявление.

**Чего он измерить не может, и это тоже измерено, а не предположено.** Retrieval. Индексация
сгенерированного репозитория на 200 фичах — 1 010 файлов, 2 434 чанка — и прогон всех 48 кейсов
дают precision@5 0.077 и recall@10 0.591, что выглядит как трудный корпус ровно до того момента,
когда кейсы разделены по способу написания:

| Группа кейсов | Кейсов | Precision@5 | Recall@10 | Средний ранг первого релевантного |
|---|---:|---:|---:|---:|
| Проза, написанная руками, со своим предметом | 14 | 0.457 | 1.000 | 1.00 |
| Шаблонные, против 199 почти одинаковых соседей | 30 | 0.027 | 0.433 | 7.15 |

Сгенерированный корпус попадает в один из двух бесполезных режимов. Там, где содержимое уникально,
каждый ответ приходит первым, и никакое изменение retrieval это число не сдвинет. Там, где оно
шаблонно, правильный ответ отличается от 199 неправильных одним предметным словом, и оценивается
лексическое везение, а не качество поиска. Настоящий код лежит между этими крайностями — похожий,
но не одинаковый, — и именно это свойство генератор дёшево не подделывает.

**Так сколько же кода нужно, чтобы числа retrieval что-то значили?** Дело не в количестве файлов.
Разрешение precision@5 — одно попадание из пяти на кейс, поэтому кейсов нужно около сотни, прежде
чем разница в пять пунктов станет отличима от шума, — и у каждого содержательного кейса ответ
должен конкурировать с правдоподобными альтернативами, а значит каждый такой кейс — это написанный
руками исходник со своим предметом. Цена измеряется в кейсах, а не в файлах, и в днях, а не в
сгенерированных строках. Поэтому числа retrieval в этом отчёте остаются тем, что они есть:
настоящий репозиторий, измеренный локально, с незакоммиченными кейсами и записанным происхождением.

## Ранжирование по форме чанка: измерено, но не принято

Нарезка по символам не сдвинула precision, и отсюда напрашивался вопрос: ранжирование считает
чанк, вырезанный по определению, и чанк, вырезанный окном, взаимозаменяемыми — а может, не
должно. При равном сходстве определение — лучший ответ: его границы поставил автор, а не окно,
поэтому читателю достаётся всё объявление и ничего сверх него.

**Гипотеза свою проверку выдерживает.** На двенадцати кейсах прогона формата 3 символьное
попадание релевантно 7 раз из 50, оконное — 6 из 70, то есть 14% против 9%. Если взять все пары
внутри одной выдачи, где оконное попадание стоит выше символьного, и поменять их местами, это
поднимет релевантное попадание 16 раз и опустит 12 — шум. Если ограничиться парами, разошедшимися
примерно на две позиции ранга, тот же обмен даёт 6 подъёмов против 1 опускания. Утверждение верно
ровно там, где оно сформулировано, — при сопоставимом счёте, — и растворяется, если растянуть его
дальше.

**Само вмешательство себя не окупает.** Две величины были реализованы и измерены до конца на том
же индексе формата 3, так что различалась только сторона запроса: RRF-бонус в одну позицию ранга
любому чанку с именем символа и бонус в две позиции.

| Метрика | Без бонуса | Один ранг | Два ранга |
|---|---:|---:|---:|
| Precision@5 | 0.133333 | 0.133333 | 0.133333 |
| Recall@10 | 0.750000 | 0.750000 | 0.750000 |
| Средний ранг первого релевантного | 4.750000 | 4.750000 | 4.750000 |
| Символов в ответах | 63 281 | 63 835 | 63 917 |
| Строк исходника в выдаче | 1 204 | 1 204 | 1 208 |
| Символьных попаданий из 120 | 50 | 53 | 55 |
| Релевантных попаданий из 120 | 13 | 13 | 13 |

Бонус делает ровно то, для чего сделан: от трёх до пяти оконных попаданий уступают место
символьным. И ни одно из поднятых им попаданий не оказывается релевантным. Ни одна метрика
качества не двигается ни в одну сторону, а ответ растёт примерно на 1%.

Поэтому изменение откачено, а не оставлено на величине, которая выглядит безобидно. Правило
ранжирования, за которым нет измерения, — это ручка, которую подкрутит следующий, у кого будет
теория, а этот корпус не отличает её наличие от отсутствия. Решить вопрос может корпус побольше,
а не бонус поменьше.

## Эвристические оценки токенов

Авторитетны приведённые выше исходные количества символов. Точечная оценка токенов
равна `ceil(response characters / 4)`. Интервал
`ceil(characters / 6)..ceil(characters / 3)` — инженерная эвристика, а не
статистический доверительный интервал и не результат tokenizer.

| Метрика | Без порога | Профиль | Изменение |
|---|---:|---:|---:|
| Точечная оценка токенов | 37 768 | 36 913 | -855 (-2.26%) |
| Эвристический интервал | 25 179..50 357 | 24 609..49 217 | -570 снизу, -1 140 сверху |

## Недоступная телеметрия

Время ожидания очереди брокера недоступно. `BrokerEmbeddingClient` использует значение
эмбеддинга, но не предоставляет receipt брокера сервису `SearchService`, поэтому
evaluator записывает `null` в `brokerQueueWaitMilliseconds` и явную диагностику
недоступности. Общее время включает очередь, выполнение модели и локальную работу
поиска; разделить эти составляющие по данным измерения нельзя.

## Ограничения

- Корпус — небольшая инженерная fixture для одного репозитория, а не benchmark общего
  поиска по коду.
- Порог релевантности фильтрует только векторную ветвь до RRF. Кандидаты с
  положительным lexical score по проекту остаются допустимыми, поэтому измеренная доля
  false positive для no-answer не улучшилась, хотя кандидаты с низким vector score
  были удалены.
- `responseCharacters` измеряет сформированные evaluator путь, метаданные и snippet.
  Метрика не включает nonce-обёртки MCP и непрозрачные chunk ID, поэтому пригодна для
  этого A/B, но не является полным числом байтов транспорта MCP.
- Исходные сырые артефакты не сохраняли текст snippet. Исправленное число строк
  детерминированно восстановлено по записанным неизменяемому коммиту, пути, диапазону
  строк и лимиту 12 строк; будущий вывод evaluator записывает число напрямую.
- Сохранён только один холодный и один следующий за ним тёплый запуск профиля. Оба
  реконструированных запуска без порога были тёплыми.
- В более ранней ручной заметке оператора, для которой недоступны сырые cold/warm JSON,
  записаны те же метрики качества и пропуски, но 170 457 символов ответа, точечная
  оценка 42 615 токенов и 123 489 мс. Эти полученные из памяти значения относятся к
  другому способу сбора вывода и не смешиваются с сопоставимой таблицей выше.
- Временные пути сырых JSON локальны для машины и могут быть удалены обычной очисткой
  временных файлов.
