# Local AI Developer Toolkit (LocalAi)

**Полное описание для разработчиков, работающих с Codex и Claude каждый день**

[English version](overview.md)

Документ описывает текущее состояние `main`. К пользователям изменения приезжают следующим
релизом: поставка идёт только через GitHub — изменение → релиз → установщик, — а ручные сборки
в рантайм не кладутся никогда.

---

## 1. Зачем это существует

Агент в облаке решает задачу «где в этом репозитории живёт логика X» единственным доступным ему
способом: читает файлы-кандидаты целиком. Пять промахов подряд — и в контекст уехали десятки тысяч
токенов, из которых пригодились сотни. То же с логом сборки на 600 КБ, со скриншотом ошибки, с
просьбой «перечисли все TODO в этих файлах».

LocalAi переносит именно эту работу — поиск, чтение изображений, разбор логов, механику над
известными файлами — на локальные модели, работающие на видеокарте разработчика. Облачная модель
получает не сырьё, а результат.

| Эффект | Как проявляется |
|---|---|
| Контекст тратится на рассуждение, а не на сырьё | В окно помещается задача целиком, а не половина одного файла |
| Ответ по смыслу, а не по совпадению строки | «Где обрабатывается отмена платежа» находит код, в котором нет слова «отмена» |
| Приватность по умолчанию | Локальные модели видят код; в облако уходит только то, что агент решил отправить |
| Предсказуемая нагрузка на GPU | Все локальные задачи идут через одну очередь, а не конкурируют за видеопамять |
| Один индекс на все инструменты | Codex, Claude, CLI и Git-хуки работают с одним состоянием репозитория |

Чего это **не** заменяет: чтение файла перед его правкой, сплошной текстовый поиск по известному
токену и архитектурные решения.

## 2. Что установлено на машине

![Схема: из чего состоит установка](images/overview-01-arhitektura.png)

Пятнадцать проектов с исходниками и десять тестовых; в повседневной работе важны шесть
исполняемых файлов из неизменяемого каталога версии и отдельно стоящий launcher.

| Компонент | Роль |
|---|---|
| Broker | Очередь и единственный транспорт к моделям |
| Сервер `codesearch` | Поиск и навигация по коду через MCP |
| Сервер `locallm` | Локальные модели через MCP |
| CLI `codesearch` | Индексация и поиск из командной строки |
| CLI `localai` | Подключение репозиториев, хуки, политики, диагностика, уборка, телеметрия |
| Launcher | Стабильная точка входа: клиенты регистрируются на неё, а не на путь версии |

Путь каталога версии меняется при каждом обновлении, путь launcher — никогда. Поэтому регистрация
MCP-серверов в Codex и Claude указывает на launcher.

## 3. Broker: почему всё идёт через одну очередь

Прямое обращение к endpoint Ollama не поддерживается. Причина не бюрократическая: на одной
16-гигабайтной карте две параллельные задачи к разным моделям означают выгрузку и загрузку по кругу —
обе работают в разы медленнее, чем если бы шли по очереди.

![Схема: путь одного запроса](images/overview-02-put-zaprosa.png)

Параметры ниже взяты из кода, а не из документации.

| Механизм | Как именно работает |
|---|---|
| Durable-очередь | Задача переживает падение клиента и перезапуск брокера; lease с heartbeat не даёт двум процессам взять одну задачу |
| Watchdog | Отделён от heartbeat: 10 минут молчания до первой пробы, дальше проба раз в минуту с таймаутом 10 секунд; попытка признаётся неудачной только после двух подряд подтверждённых «нездоровых» проб, неубедительная проба обнуляет счётчик |
| Резидентность | По умолчанию требуется полная: модель принимается, только если весь её объём находится в видеопамяти. Ослабления: «допустить частичную выгрузку» и «допустить CPU» |
| Планировщик | Предпочитает работу для уже резидентной модели, собирает связанные задачи 2 секунды, упорядочивает снимок по прогнозируемой длительности, принудительно включает задачи старше 15 минут |
| Контексты | Дискретные ступени от 2K до 256K токенов; ступень используется, только если preflight доказал, что runner помещается целиком |
| Эксперименты | Новый кандидат пробуется на первых десяти завершённых задачах профиля, затем пауза до решения владельца: продвинуть, продолжить, оставить только как fallback или отключить |

Частичная выгрузка модели в системную память не приводит к ошибке — она делает ответ в несколько
раз медленнее, не ломаясь. О себе она сообщает лишь потому, что об этом говорит строка отчёта —
рядом с моделью, которую называет. Именно поэтому она запрещена по умолчанию, а её разрешение
остаётся видимым в отчёте.

### 3.1 Очередь: три свойства, которые видны в работе

**Дедупликация по ключу.** Перед постановкой задачи очередь просматривает все задачи в состояниях
«в очереди» и «выполняется». Если у существующей тот же ключ дедупликации, новая **не создаётся** —
вызывающий получает идентификатор уже стоящей задачи и присоединяется к ней. Два клиента, попросившие
одно и то же одновременно, оплачивают одну работу, а не две.

**Карантин вместо порчи.** Запись задачи, которую не удалось прочитать или разобрать, не удаляется и
не чинится на месте: она переносится в карантин, а очередь продолжает работу. Поэтому одна битая
запись не останавливает конвейер и остаётся доступной для разбора. Сам карантин ограничен, как и
всё, что порождает рантайм, — по возрасту, числу записей и суммарному размеру, — с защитным
периодом, внутри которого свежую запись не удалит ничто: время посмотреть, что именно сломалось,
есть всегда. Счётчик карантина показывает
диагностика.

**Архив как передача, а не журнал.** Ответ забирается клиентом на следующем опросе, поэтому тело
ответа живёт недолго: сначала действует минимальный срок неприкосновенности, затем — возрастной и
объёмный пределы, причём удаляется именно тело, а запрос и документ состояния остаются как след.
Уборка идёт постоянно, но не чаще одного прохода в минуту и с ограничением за проход, чтобы очередь
не простаивала за хозяйственными работами.

### 3.2 Каталог моделей и маршруты

Каталог маршрутизации встроен в брокер. В текущей версии — шесть моделей и семнадцать профилей задач.

| Модель | Статус | Ступени контекста | Изображения |
|---|---|---|---|
| `qwen2.5-coder:14b` | устоявшаяся | 2K–32K | нет |
| `qwen3.5:9b` | устоявшаяся | 2K–256K | да |
| `gpt-oss:20b` | устоявшаяся | 2K–128K | нет |
| `qwen3-vl:8b-instruct-q8_0` | устоявшаяся | 2K–256K | да |
| `qwen3-embedding:8b-q8_0` | устоявшаяся | 2K–32K | нет |
| `translategemma:12b` | экспериментальная | 2K–128K | да |

Каталог также помечает модели, чьи рассуждения Ollama умеет выключать, и брокер шлёт
`think: false` ровно для них — сегодня это одна `qwen3.5:9b`. Рассуждающая модель на малых
ступенях контекста, которые предпочитает маршрутизация, может потратить всё окно генерации на
размышления и вернуть пустой ответ; у gpt-oss рассуждения не отключаются вовсе — поэтому флаг
помодельный, а не безусловный.

Маршруты — это упорядоченные списки допустимых моделей, а не одна привязка:

| Профиль задачи | Порядок моделей |
|---|---|
| Анализ кода, ревью кода | `qwen2.5-coder:14b` → `gpt-oss:20b` |
| Правка кода, разбор логов | `qwen2.5-coder:14b` |
| Переранжирование кода | `qwen2.5-coder:14b` → `qwen3.5:9b` |
| Извлечение, классификация, короткая сводка | `qwen3.5:9b` → `qwen2.5-coder:14b` |
| Синтез по нескольким файлам, планирование | `gpt-oss:20b` → `qwen3.5:9b` → `qwen2.5-coder:14b` |
| Распознавание текста, визуальный анализ | `qwen3-vl:8b-instruct-q8_0` |
| Переводы: обычный, технический, по изображению | `translategemma:12b` |
| Векторные эмбеддинги | `qwen3-embedding:8b-q8_0` |
| Точный поиск | модель не нужна вовсе — детерминированная лексика |

Отдельно существует список моделей, разрешённых к автоматической установке через очередь: сейчас в
нём одна позиция. Установить произвольную модель командой «поставь вот это» нельзя — общей команды
загрузки не существует, а уже установленные модели не удаляются.

### 3.3 Эксперименты и предохранитель

Модель со статусом «экспериментальная» не назначается молча и навсегда.

| Механизм | Правило |
|---|---|
| Партия испытаний | Кандидат работает на первых **десяти** завершённых логических задачах профиля, затем пара «профиль — модель» ставится на паузу |
| Отчёт до решения | Обратная связь до этой паузы отклоняется: решение принимается по результату партии, а не по первому впечатлению |
| Предохранитель | **Два подряд** технических отказа размыкают цепь, и кандидат перестаёт выбираться |
| Сброс предохранителя | Единственное досрочное исключение — явное решение «продолжить эксперимент» |
| Решения владельца | Продвинуть · продолжить · оставить только запасной · отключить |
| Составные задачи | Фрагменты одного перевода делят общий идентификатор потока и расходуют одну попытку — после итоговой проверки, сохраняя исходную категорию отказа |

Техническая, структурная и контекстная ошибки запускают запасной путь по установленному порядку
моделей. Как часто он срабатывает на конкретной машине, показывает `localai telemetry`.

## 4. Индексация

### 4.1 Что вообще попадает в индекс

Индексируются только разрешённые расширения — около пятидесяти: исходники (C#, TypeScript/JavaScript,
Python, Go, Java, Kotlin, Rust, Ruby, PHP, C/C++), разметка и шаблоны (XAML, XML, Razor, CSHTML,
HTML, CSS/SCSS/LESS), запросы и схемы (SQL, GraphQL, Proto), документация (Markdown, TXT, AsciiDoc),
конфигурация (YAML, TOML, INI, JSON), скрипты (PowerShell, Bash), инфраструктура (Terraform, Bicep) и
файлы проектов.

Намеренно исключены: файлы блокировок пакетов, минифицированные бандлы, дизайнерские и сгенерированные
C#-файлы. Они дают десятки тысяч чанков и никогда не отвечают на вопрос, который кто-то задаёт.
Файл с нулевым байтом внутри отбрасывается как двоичный, даже если у него текстовое расширение.

### 4.2 Как режется на чанки

![Схема: как исходники превращаются в чанки](images/overview-05-chanking.png)

| Тип файла | Правило |
|---|---|
| C# | Свой чанк получает тип целиком (с полями и оглавлением членов) и каждый **исполняемый** член: метод, конструктор, деструктор, оператор, оператор преобразования, индексатор и свойство **с настоящим телом** |
| C#: чего своего чанка не получает | Поля и авто-свойства — они едут внутри чанка типа. DTO с двадцатью свойствами не должен превращаться в двадцать один бесполезный вектор |
| C#: сгенерированный код | Не индексируется вовсе — разбор прерывается до первого чанка |
| TypeScript и Python | Чанк на определение по границам, которые сообщает внешний индексатор: настоящий символ, сигнатура и точные строки. Определение, содержащее другие, перечисляет вложенные, а не повторяет их тела |
| TypeScript: объявление без сообщённых границ | `scip-typescript` не сообщает тела для объявления, инициализированного вызовом, — а это и есть `export const X = memo(...)`. Такое объявление всё равно получает свой чанк: граница читается по файлу, до строки перед следующим объявлением, которое назвал индексатор |
| TypeScript: чего чанка не получает | Объявление внутри тела функции (индексатор даёт ему `local N` — ни имени, ни границ) и объявление, уместившееся в одну строку: одна строка — не тело, а вектор на строку не окупается. И то и другое остаётся на окне |
| Всё остальное, и любой участок без определения | Скользящее окно по строкам: **60 строк в окне, 12 строк перекрытия**, то есть шаг 48 строк. Синтаксис не разбирается, но точные номера строк сохраняются — именно они делают попадание пригодным к действию |

Перекрытие существует для того, чтобы смысл не терялся на границе окна.

**Что даёт нарезка по символам и чего она не даёт.** Границы не выдумываются разборщиком — они
берутся из индекса навигации, который и так строится перед эмбеддингом. Попадание в языке,
нарезанном по символам, называет тип, член или определение, из которого пришло; оконное —
файл и диапазон строк. Не каждый участок покрывается символом, и для непокрытых окно
по-прежнему верно: импорты, код уровня модуля, промежутки между функциями и то, для чего
индексатор не даёт ни имени, ни границ.

Цена нарезки по символам — корпус больше: определение получает собственный вектор, а не делит
окно с соседями. Смена формата чанков пересобирает базовое поколение целиком.

Что помогает независимо от нарезки: перекрытие в 12 строк не даёт потерять смысл ровно на
стыке окон; в текст чанка добавляется заголовок с путём и диапазоном строк, поэтому вектор «знает»
своё происхождение; лексическая ветвь поиска сверяет слова запроса с именем символа,
сигнатурой, телом чанка и путём файла — именно в таком порядке веса; а точная навигация — отдельный
слой, и она TypeScript и Python понимает.

### 4.3 База, overlay и dirty-overlay

![Схема: база, overlay ветки и незакоммиченный код](images/overview-03-indeks.png)

Порядок выбора базы проверен по коду: сначала ref, записанный в манифесте репозитория, затем локальная
`dev`, затем локальная `main`. Продвижение удалённой ветки само по себе базу не переключает.

Репозиторий определяется по нормализованному общему каталогу Git, поэтому Claude, Codex, CLI и все
worktrees используют один идентификатор репозитория и один индекс.

### 4.4 Поддержание в актуальном состоянии

Общие Git-хуки — после коммита, слияния, перезаписи истории и переключения ветки — вызывают
синхронизацию: хук запускает тот же `localai sync`, что и командная строка, в своём процессе, и Git
ждёт его завершения. Ничего не откладывается в очередь. Сам хук никогда не обращается
к моделям напрямую. Установка хуков — явная операция, только с согласия. Две синхронизации одного
репозитория не переплетаются: вторая недолго ждёт и выходит с именованным исходом «репозиторий
занят», не тронув общего состояния, — вместо того чтобы штамповать свой сбой поверх истории
чужого прогона.

Ставятся они туда, куда git действительно смотрит. Обычно это `$GIT_DIR/hooks`, но если в репозитории
задан `core.hooksPath` — а его задают husky, lefthook и simple-git-hooks, причём husky делает это из
`npm install`, — хуки идут туда. Для husky это каталог `.husky`, а не `.husky/_`, который он
пересоздаёт при каждом запуске. Существующий хук с тем же именем не затирается: он сохраняется рядом
и вызывается первым, а ненулевой код возврата от него останавливает цепочку.
Не устанавливается ничего в одном случае: рядом с чужим хуком уже лежит копия, сохранённая
при прошлой установке. Сохранить первый, не затерев второй, нельзя, поэтому команда
останавливается, называет оба файла и оставляет выбор тому, кто его делает. Файлы, попавшие
в рабочее дерево, дописываются в `.git/info/exclude`, чтобы не появляться в `git status`.

### 4.5 Поиск

Гибридный: векторное сходство плюс лексическое совпадение. Векторная ветвь отсекается порогом,
**откалиброванным для конкретной модели эмбеддингов**; если профиля для модели нет, поиск отказывает,
а не заимствует чужой порог. Кандидаты с положительным лексическим score допускаются и при низком
векторном — так работает запрос по точному имени символа.

Перед выдачей проверяются идентификатор репозитория, поколение, дерево, модель, размерность, формат и
контрольная сумма. Смешать новую базу со старым overlay или молча ответить по устаревшему коду нельзя.

Загруженный индекс освобождает память автоматически после 10 минут без запросов; освободить его
немедленно можно отдельным инструментом, файл на диске при этом не трогается.

Когда ни одна модель эмбеддингов не отвечает, векторная ветвь работать не может, и поиск
переходит на чисто литеральное совпадение, а не отказывает: лексические попадания лучше
исключения. Ответ об этом говорит прямо и перестаёт называть модель эмбеддингов — модель берётся
из заголовка индекса, поэтому напечатать её после того, как ничего не считалось, значит отчитаться
о сравнении, которого не делали. Пустой результат несёт ту же строку, и это самый важный случай:
у запроса на естественном языке почти нет литералов для совпадения, поэтому «ничего не найдено» в
этом состоянии означает, что не отработала та половина инструмента, которая отвечает на такие
вопросы, а не что в репозитории нет такого кода.

### 4.6 Точная навигация и её честная деградация

Переход к определению обязан отличаться от текстового поиска, поэтому у навигации три источника и
строгий порядок между ними.

| Источник | Когда работает | Точность |
|---|---|---|
| Живой языковой сервер | Пока документ открыт соответствующим инструментом. Выключен по умолчанию, включается отдельным файлом настроек | Авторитетный |
| Снимок точной навигации | Строится вместе с поколением индекса: C# и XAML разбираются напрямую, TypeScript и Python импортируются из внешних индексаторов | Точный |
| Ограниченный текстовый поиск | Только когда первые два не ответили | Помечается как эвристический |

Отдельно — то, что связывает поиск с навигацией. Попадание поиска называет путь и диапазон строк, но
не колонку идентификатора внутри строки, поэтому естественный вызов — колонка 0. Позиция, которая сама
ничего не называет, разрешается в объемлющее объявление строки — для однострочной сигнатуры это метод,
а не его параметры, — и именно поэтому начальная строка попадания годится для навигации как есть.
Строка объявлений-соседей (`const a = f(), b = g()`), где ни одно не содержит другое, однозначного
ответа не имеет — там возвращается уведомление о деградации, а не первое попавшееся из двух.

Два исключения: поиск реализаций и поиск связей текстового приближения не имеют вовсе — здесь
правдоподобный ответ хуже пустого. Когда ответ получен эвристикой, он прямо называет причину, и две
возможные причины сформулированы по-разному, потому что лечится только одна: поколение, собранное до
появления точной навигации, чинится пересинхронизацией, а отсутствие символа в указанной позиции —
нет.

работа ушла вниз, а не только что она сделана.

### Как устроен разбор длинного лога

Лог не обязан помещаться в контекст модели — ни в один, ни целиком в память.

1. **Выбор ступени.** Брокер проверяет настроенные ступени контекста от большей к меньшей и берёт
   наибольшую, для которой доказана полная резидентность на этой машине.
2. **Нарезка.** Файл читается потоком и режется на фрагменты под выбранный контекст, с перекрытием —
   чтобы ошибка, разорванная границей фрагмента, не потерялась.
3. **Последовательный разбор.** Каждый фрагмент идёт через общую очередь строго по порядку.
4. **Ограниченная свёртка.** Частичные результаты объединяются иерархически, поэтому в памяти не
   лежит ни весь лог, ни неограниченный список сводок; повторяющиеся свидетельства схлопываются.

Поведение настраивается файлом политики, который читается **перед каждым вызовом** — без пересборки и
перезапуска. В нём задаются потолок контекста, резерв под ответ, оценка символов на токен, предельные
размеры фрагмента, перекрытия и частичной сводки. Значения по умолчанию: потолок 256K токенов, резерв
4096, консервативные 2.0 символа на токен, фрагмент до миллиона символов, перекрытие до 2048.

Важно: настроенный контекст — это только потолок. Он не отменяет проверку резидентности, и если
большая ступень не подтвердилась, конвейер спускается к меньшей, а не уезжает в системную память.

## 6. Защиты

### 6.1 Граница недоверия вокруг исходников

Код репозитория — данные, а не инструкции. Но в комментарии может лежать «игнорируй предыдущие
инструкции», а в чужом vendor-каталоге — что угодно. Поэтому всё, что получено из исходников,
возвращается внутри отдельного блока, помеченного случайным 96-битным одноразовым значением.

![Схема: граница недоверия вокруг исходников](images/overview-04-granica-nedoveriya.png)

Как это устроено на самом деле:

| Свойство | Поведение |
|---|---|
| Источник метки | Криптографический генератор, 12 байт |
| Проверка уникальности | Метка проверяется на отсутствие в самом содержимом — до десяти попыток; если не нашлась, вызов завершается ошибкой, а не отдаёт подделываемую границу |
| Экранирование источника | Атрибут с путём экранируется целиком, включая управляющие символы, — путь не может закрыть тег |
| Симметрия маркеров | Открывающий и закрывающий маркеры несут одну метку, поэтому вставить «свой» закрывающий тег в исходник невозможно |
| Что остаётся снаружи | Только доверенное: сводка индекса, диагностика, ошибки валидации |

**Границу используют десять инструментов.** На сервере `codesearch`: поиск, получение чанка,
переход к определению, поиск ссылок, поиск реализаций и поиск связей — пути, идентификаторы
символов и диапазоны написаны тем же, кто написал репозиторий, поэтому они — такие же данные, как
фрагмент кода. На сервере `locallm`: `read_image`, `triage_log`, `ask_local` и `translate_local`
— локальная модель читала файлы, логи или изображения, а слабая модель может повторить или
усилить подброшенную в них инструкцию, поэтому её ответ приходит внутри той же границы, а строка
notice остаётся снаружи — это слова самого процесса.

### 6.2 Идентификатор результата

Идентификатор чанка непрозрачен и содержит репозиторий, поколение, дерево, хеш незакоммиченного
содержимого и порядковый номер, плюс контрольную сумму полезной нагрузки.

Важная точность, записанная прямо в коде: контрольная сумма — **не граница аутентификации**. Она ловит
случайное повреждение и небрежную подделку. Право прочитать исходник даёт другое — совпадение
репозитория, поколения, дерева и dirty-overlay, проверяемое до любого чтения. Идентификатор из другого
репозитория, из старого поколения или с номером вне диапазона отклоняется, а не разрешается
по другому снимку.

### 6.3 Транспорт, права и поставка

| Рубеж | Что обеспечивает |
|---|---|
| Единый транспорт | Единственный путь к моделям — broker; agent-facing endpoint Ollama не поддерживается |
| Права рантайма | Каталоги приводятся к ожидаемому виду и проверяются одним проходом. Раздельные проходы давали окно гонки: параллельно работающие Claude и Codex ловили ложный отказ проверки прав |
| Чистота протокола | MCP-серверы резервируют стандартный вывод под протокол |
| Подпись релиза | Публичный ключ вшит в сами бинарники, а не лежит файлом рядом: подложить пакет, подписанный чужим ключом, нельзя |
| Неизменяемые версии | Каталог опубликованной версии никогда не переписывается; откат — активация ранее проверенного каталога |
| Атомарное переключение | Активация требует явно указать, какой указатель заменяется, поэтому параллельную активацию нельзя молча перезаписать |
| Мягкая остановка | Broker просят завершиться: он замечает запрос на своём ежесекундном heartbeat, перестаёт брать новую работу и доводит текущую задачу до конца. Убивают только того, кто не ушёл к сроку |
| Границы роста | Ограничены поколения индексов, установленные версии, бэкапы, архив задач, тела ответов, карантин и телеметрия |

Отдельная тонкость про хранение: минимальный срок жизни тела ответа защищает не диск, а
корректность — ответ моложе этого срока не удаляется ничем, а вручную выставленный ноль зажимается,
а не выполняется.

Только что опубликованное поколение индекса хранится сутки независимо от счётчика: его публикуют
за минуты до того, как на него переставят указатель, и уборка в этом окне удалила бы то, что
синхронизация только что строила весь свой прогон. Эта защита кончается, как только указатель
уходит дальше: поколение, опубликованное раньше текущего, своё уже отработало и убирается по
счётчику, как любое другое.

## 7. Экономия облачных токенов

### 7.1 Методика

Каждый локальный вызов сообщает, во что он обошёлся и что сберёг: какой инструмент и какая
модель отработали, сколько времени это заняло и сколько токенов не ушло в облако. Время
измерялось всё это время — брокер записывает, сколько задача ждала и сколько выполнялась, — но
попадало только в телеметрию экспериментов, поэтому строка отчёта его не называла, а тот, кто
её читал, вынужден был гадать. Теперь оно берётся из квитанции, и ожидание называется
отдельно, когда составляет заметную долю: четыре секунды за другим клиентом — повод посмотреть
на очередь, четыре секунды вычислений — на модель. `search_code` через эту очередь как раз идёт — вычисление
вектора для запроса такая же задача брокера, как любая другая, — но квитанция до инструмента
не доходит, да и время поиска этим не исчерпывается: загрузка индекса и сборка overlay
занимают остальное. Поэтому он замеряет себя сам, целиком.

Живого счётчика токенов в системе нет, поэтому любая цифра — оценка и подаётся диапазоном. Константы
пересчёта проверены по коду: **4.0 символа на токен** для латиницы, **2.2** для кириллицы, для
изображений — **площадь в пикселях, делённая на 750**. Экономия считается как «сколько стоило бы
затащить это сырьё в облачный контекст» минус «что реально потрачено».

Не путать с другой константой: у разбора логов есть собственный, намеренно консервативный коэффициент
**2.0 символа на токен**, и он служит для нарезки фрагментов под контекст модели, а не для подсчёта
экономии.

### 7.2 Измерено на конкретной машине

`localai telemetry` печатает измеренную сводку для машины, на которой запущена: как завершались
задачи, холодные и тёплые загрузки моделей, доля fallback, задержки очереди и исполнения как
перцентили ближайшего ранга и оценка экономии — по моделям и по профилям задач. Когда одна
модель с достаточным числом заданий валит не меньше четверти из них и владеет не меньше чем
половиной всех записанных отказов, сводка называет её одной строкой `attention`: больную
модель, которую fallback тихо прикрывает, иначе не видно за приемлемыми процентами успеха по
профилям. Дороже всего отдавать вниз не перевод и не распознавание текста, а работу с большими
объёмами кода и логов.

### 7.3 Расчёт по типовым задачам

Средний файл исходников — это несколько тысяч токенов, поэтому ответ на «где живёт X» чтением
десяти файлов-кандидатов целиком стоит десятки тысяч, а ответ поиска — примерно полторы тысячи.
Лог сборки в сотни килобайт — порядка 150K токенов целиком и несколько сотен в виде сводки
разбора. Полноэкранный скриншот — пара тысяч токенов пикселями и пара сотен извлечённым
текстом. Обзор незнакомого репозитория целиком уходит в миллионы токенов — с индексом такая
задача вообще становится выполнимой.

### 7.4 Честность оценок и случаи, когда экономии нет

Поиск радикально экономит контекст, но даёт хороший короткий список кандидатов, а не
гарантированно единственный правильный ответ.

| Ситуация | Почему экономии нет |
|---|---|
| Скриншот вставлен прямо в окно чата | Он уже оплачен; отдавать его после этого локальной модели бессмысленно. Просите путь к файлу |
| Очень мелкое изображение | Скриншот размером с кнопку стоит пару десятков токенов; любой полезный ответ о нём длиннее |
| Точный поиск по известному токену | Дешевле обычного текстового поиска ничего нет |

### 7.5 Телеметрия: что она собирает и чего в ней принципиально нет

Каждая делегированная задача оставляет одну запись в рантайм-каталоге. Именно из них собирается
сводка `localai telemetry`.

| Что записывается | Чего в записи нет |
|---|---|
| Идентификатор задачи, профиль, модель, размер контекста | Промпты и ответы |
| Размеры входа и выхода — **корзинами**, а не точными значениями | Содержимое файлов и байты изображений |
| Холодная загрузка, смена модели, использование запасного пути | Пути к файлам и имена репозиториев |
| Результат валидатора и исход выполнения | Секреты любого рода |
| Длительности: очередь, загрузка, исполнение, всего | — |
| Оценки токенов: валовая, на проверку, чистая | — |

Сроки: записи задач хранятся тридцать дней, записи по экспериментам — неделю. Отчёт по эксперименту
поэтому честно указывает, на скольких сохранившихся записях построены его тайминги: число попыток
берётся из состояния эксперимента и живёт дольше, чем измерения.

Экономия в сводке подаётся диапазоном и разделена на валовую, потраченную на проверку и чистую.
Сумма из ста тысяч оценок не становится точной оттого, что она большая.

## 8. Повседневные рецепты

| Ситуация | Что делать |
|---|---|
| «Где обрабатывается отмена подписки?» | `search_code` — описанием словами, а не именем символа |
| Нашли фрагмент, нужен полный текст | `get_code_chunk` по идентификатору из выдачи |
| «Кто вызывает этот метод?» | `find_references`, не текстовый поиск |
| «Какие есть реализации интерфейса?» | `find_implementations` — приблизительный ответ здесь хуже пустого |
| Упала сборка, лог на сотни килобайт | `triage_log` с путём к файлу |
| Скриншот ошибки от коллеги | Сохранить файлом, затем `read_image` по пути |
| «Собери TODO по этим восьми файлам» | `ask_local`, профиль извлечения |
| Поиск отвечает странно | `index_status`: не отстал ли индекс от HEAD |
| Долгая пауза в работе, память жалко | `index_unload`; на диске индекс остаётся, следующий поиск перечитает его примерно за секунду |

**Новый репозиторий.** Сначала read-only проверка состояния (`localai repo status --root <репозиторий>`).
Если не
подключён — синхронизация (`localai sync`) и установка хуков (`localai hooks install`), обе операции
требуют явного согласия. Пока строится первое поколение, состояние называется «инициализация»:
отвечать по частичному индексу нельзя, правильный ответ агента — «репозиторий ещё индексируется».

**Диагностика.** Команда `localai doctor` проверяет версию и целостность бинарников, стабильную точку
входа, живость брокера, очередь и карантин, действующие политики и состояние индекса. Она только
читает и ничего не запускает; остановленный broker помечается как заметка, а не ошибка, потому что он
стартует по требованию. Живой брокер и движущаяся очередь — разные вопросы, и задаются оба:
задания, прождавшие дольше возраста, начиная с которого планировщик принудительно берёт
заголодавшее, и ни разу не взятые в работу, — это не занятая очередь, а необслуживаемая.

**Уборка.** `localai prune` освобождает место по границам хранения; предварительный просмотр —
с ключом сухого прогона. Указатель активной версии и текущее поколение индекса он не трогает, а
оверлеи, на которых не находится ни один живой worktree, забирает — и оставляет оверлеи
репозитория нетронутыми всякий раз, когда не может установить, какие worktree у него живы.

**Делегирование локальной модели из терминала.** `localai ask` выполняет механическую работу над
названными файлами — обобщить, перечислить все методы, которые делают X, собрать TODO;
`localai triage` читает лог и говорит, что упало и почему; `localai read-image` читает скриншоты,
отсканированные страницы и схемы. Все они идут к тому же брокеру, той же маршрутизации и тем же
моделям, что и инструменты MCP, потому что вызывают тот же код:

| Инструмент MCP | Консоль |
| --- | --- |
| `ask_local` | `localai ask "<инструкция>" [файл ...]` |
| `triage_log` | `localai triage [файл-лога\|-]` |
| `read_image` | `localai read-image "<вопрос>" <изображение> [изображение ...]` |
| `translate_local` | `localai translate [текст\|-] --from <язык> --to <язык>` |

Это же соответствие уходит в машинном виде — как `commands[].tool` в перечне возможностей из
§8.1, — так что таблица здесь его читаемая сторона, а не второй список, который надо
поддерживать.

У `read-image` вопрос идёт первым, как у `ask`. Первый аргумент, который сам является путём к
изображению, читается как забытый вопрос, а не как вопрос: `localai read-image shot.png` скажет,
что не хватает вопроса, — именно этого и не хватает. А вопрос, который просто заканчивается именем
файла, содержит пробел и остаётся вопросом.

Пока сервер MCP работает, инструмент остаётся первым выбором. Эти команды существуют для человека
за приглашением командной строки и для агента, у которого сервер MCP не запущен, — это тот запасной
путь, которым продукт велит пользоваться на каждой машине.

Когда файл не назван, `triage` читает стандартный ввод, и эту форму стоит запомнить:

```powershell
dotnet build 2>&1 | localai triage
```

**Ответ идёт в стандартный вывод, а сообщение о ходе работы — в стандартный поток ошибок**,
поэтому `localai ask "обобщи" src/Foo.cs > summary.md` оставляет файл, в котором только ответ.
Сообщение называет модель, объём обработанного, длительность и сэкономленное; оно в потоке ошибок,
потому что говорит о запуске, а не о результате.

**Перенаправленный ответ несёт метки происхождения, ответ на терминал — нет.** Ответ написан
локальной моделью по прочитанным ею файлам, поэтому там, где его смогут прочитать снова — в файле,
в конвейере, в другой программе, — он приходит завёрнутым в те же метки `<untrusted-content>` с
одноразовым идентификатором, что и у инструментов MCP, и ничто внутри них нельзя считать
указаниями. На терминале читатель — человек, и метки там только мешают, поэтому их нет.

То же правило теперь распространяется на `codesearch get-chunk`, который печатает байты
исходного файла и потому опаснее всего в смысле внедрения указаний: до сих пор он печатал их
без меток в любую сторону.

**`translate` — исключение, и ради него есть `--out`.** Его ответ — это документ, а не
высказывание о документе, поэтому перенаправление сохранило бы файл, полный меток. `--out <файл>`
пишет сам документ, без обёртки; без этого ключа перенаправленный перевод заворачивается, как
любой другой ответ, и команда говорит об этом в потоке ошибок. `--from` и `--to` принимают
*названия* языков: значение уходит модели как написано, поэтому `--to ru` не падает — он даёт
английскую атрибуцию на русском документе.

**Каждый перевод заканчивается абзацем атрибуции** с названием модели. Он безусловен, он есть в
обоих лицах и попадает внутрь того, что пишет `--out`. Машинный перевод, который можно принять за
человеческий, — ровно то, что этот абзац предотвращает.

Коды возврата — значения sysexits, а не произвольный набор. Если для профиля, к которому ведёт
команда, не установлено ни одной модели, код возврата — **69**, и сообщение называет команду
установки; это не то же самое, что неверный аргумент, где код 2. Перевод, структура которого после
повторов всё ещё неверна, даёт **65** — тот же код, что и отвергнутый фрагмент: модель выдала
данные, которыми нельзя воспользоваться. Файл `--out`, который не удалось записать, даёт **73**,
потому что командная строка была верной, а причина — права или отсутствующий каталог.

### 8.1 Ответ программе

Всё, что выше, написано для человека, и с тех пор как консоль стала отвечать на языке читателя,
она не может быть ещё и контрактом: парсер сломается на первой же русской машине. `--json` —
вторая её сторона. Он для плагина редактора, скрипта или задачи по расписанию — для всех, кто
читает ответ, а не смотрит на него.

Один конверт, какой бы ни была команда:

| Поле | |
| --- | --- |
| `schema` | версия конверта, целое число. Добавление поля её не меняет; удаление, переименование и смена типа — меняют |
| `command` | команда, как её набрали, без опций — `repo status`. Пусто, только если команды не было вовсе |
| `ok` | получил ли запуск свой ответ. Это не вердикт: запуск, чей ответ — «эта установка сломана», остаётся `ok: true`, а вердикт лежит в `data` |
| `data` | собственный ответ команды. Отсутствует, когда `ok` равно false |
| `error` | `code` и `message`. Отсутствует, когда `ok` равно true |

**`--json` заодно фиксирует язык на английском.** Версионируемый вывод не может следовать за
машиной, с которой пришёл, поэтому флаг решает и то и другое. Читатель, задавший
`LOCALAI_LANGUAGE=ru` и запросивший JSON, получит русскую прозу везде, кроме конверта, — так и
задумано. Одно исключение стоит знать: ошибку Windows, приходящую через `Win32Exception`,
операционная система описывает своими словами, поэтому такие сбои получают код и собственную
фразу LocalAi раньше, чем дойдут до конверта.

**Флаг есть в обоих бинарях, и конверт у них один.** `localai` и `codesearch` отвечают одними и
теми же `schema`, `command`, `ok`, `data` и `error`, поэтому плагин пишет один парсер на оба. Две
вещи всё же различаются: `localai` под `--json` фиксирует язык на английском, а `codesearch`
фиксирует английский для всего, что печатает, — проза вокруг сообщений его индексного ядра
по-прежнему состоит из английских литералов, и одна русская фраза внутри английского ответа хуже,
чем ни одной; и коды возврата — разные словари: `localai` пользуется значениями sysexits,
`codesearch` на любую неудачу возвращает 1. `ok` в обоих значит одно и то же — запуск получил свой
ответ; не переносятся именно числа.

Инструменты MCP — вторая половина того же и ведут себя наоборот: они переведены целиком и следуют
за читателем, поэтому один и тот же отказ одного и того же индексного ядра приходит по-русски
через `search_code` и по-английски через `codesearch search`. Так и задумано: первое читает
человек на своём языке, второе разбирает программа.

**Новые коды могут появиться в любом релизе**, поэтому у вызывающего должна быть ветка для
незнакомых. Именно это превращает последующее дробление слишком общего кода — когда один
`input_rejected` станет несколькими — в добавление, а не в поломку.

**`code` — чтобы ветвиться, `message` — чтобы показать человеку.** Разбирать `message` нельзя:
его переписывают всякий раз, когда он оказался неясен, и это не изменение схемы. Коды устроены
как `subject_state` — `root_value_missing`, `repository_ambiguous`, `argument_unknown` — и никогда
не называют команду: её уже несёт конверт, а один и тот же отказ повторяется у разных команд.

**Коды возврата не меняются**, и `ok` — не один из них. Он говорит, что запуск получил свой
ответ, а это не то же самое, что хороший ответ; две команды показывают, как эти вещи расходятся.
`localai sync` печатает `REFUSED …` и выходит с нулём намеренно: запуск, обоснованно отказавшийся
что-то делать, сделал ровно то, о чём его просили, — это `ok: true`, а отказ лежит в `data`.
`localai doctor` выходит с единицей, когда проверка провалилась: это вердикт о машине, а не о
запуске, и он тоже `ok: true`, а провалившиеся проверки лежат в `data` — там, где они вызывающему
нужнее всего. `ok: false` остаётся за запусками, которые не дали ответа вовсе: отклонённый
аргумент, недоступный брокер, непредвиденный сбой.

**Команды, которые `--json` не отвечают, отказывают**, а не печатают прозу, поэтому обещание
выполняется без исключений: если флаг передан, в стандартном выводе — конверт. В блоке Usage
команды, принимающие его, отмечены как `[--json]`; сегодня это `localai repo status`,
`localai doctor`, `localai ask`, `localai triage`, `localai read-image`, `localai translate`,
`codesearch search`, `codesearch get-chunk` и `codesearch status` — и ещё `capabilities` в
обоих бинарниках, которая стоит там без скобок, потому что флаг у неё обязателен, а не
необязателен:

```json
{"schema":1,"command":"repo status","ok":true,"data":{"repositoryId":"0ecc9019…","commonDirectory":"R:\\LOCALAI\\.GIT","status":"CONFIGURED"}}
```

| `data` | |
| --- | --- |
| `repositoryId` | идентификатор, которым названы все каталоги рантайма и который печатает `SYNCED repository=` |
| `commonDirectory` | о каком репозитории этот ответ — в написании идентичности: абсолютный путь, родные разделители, на Windows в верхнем регистре. Плагин, сравнивающий его со своим путём, обязан сравнивать без учёта регистра |
| `status` | `CONFIGURED` или `NOT_CONFIGURED` — тот же токен, что печатает проза |

`doctor` наполняет его отчётом — по объекту на проверку; здесь три из девяти:

```json
{"schema":1,"command":"doctor","ok":true,"data":{"verdict":"Failed","failed":1,"warned":3,"checks":[{"name":"version","status":"Failed","detail":"The pointer names 0.1.51 and that directory does not exist.","versionDirectory":"0.1.51"},{"name":"queue","status":"Warning","detail":"4 queued, 2 quarantined. Quarantined jobs are never retried.","queued":4,"quarantined":2},{"name":"repository","status":"Warning","detail":"R:\LocalAi is not connected. Index it: localai sync --root R:\LocalAi","repositoryId":"0ecc9019…","repositoryRoot":"R:\LocalAi","state":"NotConfigured"}]}}
```

| `data` | |
| --- | --- |
| `verdict` | `Ok`, `Warning` или `Failed` — отчёт одним словом. Предупреждение — не отказ: незапущенный брокер стартует по требованию |
| `failed`, `warned` | сколько проверок вернулось с каждым исходом |
| `checks[]` | по объекту на проверку, в порядке печати отчёта. В любом релизе может появиться новая; незнакомое имя вызывающий пропускает |

| Проверка | |
| --- | --- |
| `name` | `version`, `launcher`, `broker`, `queue`, `policy.models`, `policy.retention`, `policy.languageServers`, `update`, `repository` — последняя только если был передан `--root` |
| `status` | `Ok`, `Warning` или `Failed` |
| `detail` | строка, которую для этой проверки печатает проза, по-английски. Её показывают человеку и никогда не разбирают — то же обещание, что у `error.message` |
| остальное | то, что установила проверка: `versionDirectory`, `releaseVersion` и `missingFiles` у `version`; `path` у `launcher`; `processId` и `heartbeatAgeSeconds` у `broker`; `queued`, `quarantined` и `oldestUnattemptedMinutes` у `queue`; значения самой политики и `fileFound` у трёх политик; `enabled`, `availability`, `latestVersion`, `releaseUrl` и `checkedAtUtc` у `update`; `repositoryId`, `repositoryRoot`, `state` и `generationId` у `repository`. Поле отсутствует, когда проверка не смогла его установить; `null` не пишется никогда |

**`fileFound` говорит, что файл был, а не что его прочитали.** Любое хранилище политик отвечает на
испорченный документ своими значениями по умолчанию, а не ошибкой, поэтому переставший разбираться
файл считается найденным, и рядом стоят значения по умолчанию.

**Код возврата здесь — вердикт.** 0, когда ничего не провалилось, 1, когда провалилось; `ok: true`
в обоих случаях. `ok: false` от этой команды значит, что отчёта не получилось вовсе.

`ask` и `triage` наполняют тот же конверт ответом и стоимостью запуска:

```json
{"schema":1,"command":"ask","ok":true,"data":{"answer":"…","origin":"ask:R:\\repo\\src\\Foo.cs","model":"qwen3.5:9b","residency":"None","queuedMs":2241,"ranMs":5230,"savedTokensEstimate":253,"truncated":false}}
```

| `data` | |
| --- | --- |
| `answer` | что ответила модель, без обёртки: метки прозаической стороны — граница для текста без структуры, а здесь границей служит сама структура |
| `origin` | команда и то, что она прочитала, — то же значение, которое проза кладёт в атрибут метки |
| `model` | модель, которая действительно отработала, — не всегда та, которую предпочитает профиль |
| `residency` | `None`, `PartialOffload` или `Cpu` — сколько модели поместилось в видеопамять. Всё, кроме `None`, означает, что ответ был медленнее, и запуск об этом сказал |
| `queuedMs`, `ranMs` | ожидание и работа по отдельности: четыре секунды за чужим клиентом — повод посмотреть на очередь, четыре секунды вывода — повод посмотреть на модель |
| `savedTokensEstimate` | оценка, и названа так: она считается по символам, поэтому вывести её как точное число токенов значило бы солгать о точности |
| `truncated` | сформирован ли ответ по части входных данных, потому что общий бюджет исчерпан. Присутствует всегда; усечь может только `ask`, поэтому у `triage` и `read-image` там всегда `false` |
| `vramResidentPercent` | сколько модели поместилось в видеопамять; присутствует, только когда `residency` не `None`. Вердикт говорит, что запуск был ухудшен, а это — насколько |

`translate` наполняет тот же конверт тремя числами вместо одного —
`savedTokensEstimate`, `localTokensProcessedEstimate` и `netContextTokensSavedEstimate`, все
названы оценками по одной и той же причине, — и без `truncated`: перевод разбивает весь вход и
ничего не отбрасывает. В его `answer` входит абзац атрибуции.

При `--json` в стандартный поток ошибок не пишется ничего, поэтому всё, что там появилось,
вызывающий вправе считать аномалией.

Сама фраза в `data` не попадает. Это указание агенту, её переписывают всякий раз, когда она
оказалась неверна, и версионируемый контракт — неподходящее для неё место.

Две вещи старше этого флага и им не являются. `localai model` всегда печатал собственный конверт
JSON — без флага и без прозаической стороны, — и ещё один печатает `codesearch evaluate`. Оба
называют поле версии `schemaVersion`, тогда как здесь оно `schema`, и именно имя поля различает
все три. Это несвязанные формы со своими читателями — первую разбирает `BrokerModelInstaller`, — и
`--json` не принимает ни одна.

Общий конверт наполняют `codesearch search`, `get-chunk` и `status`. В `data` у `search` — `query`,
`embeddingsUsed` и `hits[]`, причём `embeddingsUsed` обязателен, а не полезен: в прозе предупреждение
`LEXICAL ONLY` уходит в поток ошибок, когда ни одна модель эмбеддингов не ответила, а при `--json`
поток ошибок пуст — без этого поля вызывающий показал бы буквальные совпадения как ранжированные.
Поле `score` сравнимо внутри одного ответа и несравнимо между ответами. У `get-chunk` те же поля
плюс `body`. У `status` — `connected` (`CONFIGURED` или `NOT_CONFIGURED`, тот же токен, что печатает
`localai repo status`), `built`, `stale`, `navigation` (`Precise` или `Heuristic`), модель и её
размерность, счётчики, коммиты и вложенный `overlay`.

**Узнать, на что отвечает бинарник, не зашивая это у себя.** `capabilities` перечисляет команды,
которыми программа может управлять:

```json
{"schema":1,"command":"capabilities","ok":true,"data":{"binary":"localai","commands":[{"name":"ask","shape":"schema","tool":"ask_local"},{"name":"model status","shape":"schemaVersion","tool":"local_models_status"}]}}
```

| `data` | |
| --- | --- |
| `binary` | `localai` или `codesearch`. Оба отвечают с `command: "capabilities"`, поэтому без этого поля два перечня неразличимы |
| `commands[].name` | путь команды ровно в том написании, в каком его печатает поле `command` самого конверта, — чтобы вызывающий мог сопоставить одно с другим |
| `commands[].shape` | буквальное имя поля версии в выводе этой команды: `schema` у общего конверта, `schemaVersion` у двух форм, которые старше него. Это не категория, а то свойство, которое читают первым |
| `commands[].tool` | инструмент MCP, делающий ту же работу; отсутствует, когда такого нет. У `model pull` его нет: `local_models_sync` ставит в очередь набор недостающих рекомендованных моделей, а не названную; `codesearch status` соответствует `index_status` и отвечает больше, чем тот инструмент, поэтому откат на инструмент даёт более узкий ответ, а не неверный |

**Это два вызова, по одному на бинарник.** Ни одна консоль не ссылается на другую и не может
честно описать поверхность, которой не видит: перечень «за двоих» был бы зашитой копией команд
соседа — ровно тем, ради устранения чего всё это и сделано.

**Отсутствие означает «программа не может этим управлять», а не «не установлено».** Команда без
машинной формы — это команда, которой плагин воспользоваться не может, потому что разбор прозы и
есть то, чего флаг позволяет избежать. Всё, что может запустить человек, перечислено в блоке
usage, и синтаксис несёт он, а не этот перечень.

**Поля версии здесь нет намеренно.** Список команд и есть определение возможностей, и, в отличие
от сравнения версий, устареть он не может. Версия для отчёта об ошибке приходит от
`localai doctor`: он сообщает, какую версию называет активный указатель и полна ли эта установка.

**Флаг здесь обязателен, а не необязателен** — потому в строке usage он без квадратных скобок. Без
него команда отказывает с кодом `json_required` и называет блок usage, список для человека. Сам
`json_required` — единственный код, который никогда не приходит внутри конверта: условие, его
порождающее, — это как раз отсутствие конверта.

## 9. Установка и обновление

![Схема: установка и обновление](images/overview-06-ustanovka.png)

Вручную останавливать ничего не нужно: установщик сам гасит broker и MCP-серверы — тогда и
только тогда, когда они мешают, — и заменяет их.

Поставка идёт только через GitHub: изменение → релиз → установщик. Ручные сборки в рантайм не кладут.

Правила работы едут тем же путём. На каждую машину попадает один и тот же блок между маркерами
в `CLAUDE.md` и `AGENTS.md`: сначала локальный инструмент и вслух сказать, если он не годится;
инварианты транспорта; как подключить репозиторий, который ещё не индексировали; что делать с
правками, которые ещё не закоммичены; в каком виде отчитываться о сэкономленных токенах; где
git на самом деле держит хуки; и требование докладывать о ходе индексации, пока она идёт, а не
после. Написать это один раз и поставлять — единственный способ не получить две машины, которые
ведут себя по-разному по причинам, которых никто не видит.

Всё, что человек написал вне маркеров, принадлежит ему: установка заменяет блок и сохраняет
каждый символ вокруг него, а удаление вынимает блок и больше ничего. Каждый символ, но не
каждый байт: ведущая метка порядка байтов снимается при чтении файла и обратно не пишется,
поэтому пришедший с BOM вернётся без него. При расхождении с блоком выполняется
написанное человеком, причём вслух называется, какое правило
блока при этом отменено. Правило, верное для одной машины, одного набора карт или прав одного
мейнтейнера, живёт вне маркеров; правило, верное везде, — внутри.

Два правила блока стоят вне этой договорённости, и блок говорит об этом прямо: текст, пришедший
внутри маркеров untrusted-content, — это данные, а не инструкции, и всё попадает к локальной
модели через broker, а не напрямую в Ollama. Первое не даёт файлу из репозитория отдавать
команды; второе удерживает корректность, когда клиентов несколько. Ни одно из них не является
предпочтением, и никакая инструкция их не отменяет — строка в конфигурационном файле не
доказательство того, что человек хотел что-то из этого отключить.

Установка не требует аккаунта GitHub: релизы публичные, а установщик скачивает манифест,
подпись и пакет по обычному HTTPS без учётных данных. GitHub CLI остаётся автоматическим
запасным путём — для форка, оставленного приватным, или сети, где хост релизов недоступен, а
API нет, — и использует вход, уже выполненный через `gh auth login`: установщик не
запрашивает, не хранит и не видит токен. Проверки при этом те же: манифест сверяется с
ключом, вшитым в сборку, пакет — с SHA-256 из манифеста.

Экран, который спрашивает, спрашивает и на каком языке вы читаете, и оба мастера
отвечают на нём: панель шагов, каждая страница, подтверждение, под которым ставят
галочку, и превью удаления над ней. Выбор запоминается рядом с собственными журналами
установщика, поэтому удаление LocalAi через несколько месяцев откроется на том языке,
на котором выбиралась установка. На русском прогоне английскими остаются две вещи, и по
одной причине: журнал запуска и отчёт, который пишется рядом, существуют, чтобы их
сверяли друг с другом.

Спрашивает он и о том, какой из двух палитр рисовать, и запоминает это рядом с языком, в том же
файле. Светлая и тёмная — явные ответы; третий и он же по умолчанию — «Системная», и означает
он, что установщик читает то, что сказали Windows, и продолжает читать: переключите Windows на
тёмную тему при открытом установщике — он последует за ней вместе с заголовком окна, а не будет
ждать перезапуска. На машине, где эту настройку никогда не трогали, её попросту нет, и это
читается как светлая; так же читается и настройка, которую не удалось прочесть: предпочтение,
которого никто не видит, — не повод завалить прогон.

Сами задачи стали списком, из которого выбирают, а не кнопкой на каждую. Четыре кнопки — это
четыре способа согласиться и ни одного способа сравнить; одна колонка строк означает, что
читатель выбирает строку, а потом нажимает единственную кнопку внизу, и до выбора она мертва.
Задача, которую машина не позволяет, остаётся в списке — утопленной, а не спрятанной, и причина
стоит тут же рядом: спрятать её значит заставить человека искать то, что перед ним. Когда
выполнима ровно одна задача, её выбор — не вопрос, поэтому экран отвечает на него сам, и кнопка
жива сразу.

«Назад» на первой странице мастера возвращает к этому списку, и выбор на нём остаётся. К этому
моменту ничего ещё не изменено, а любой выбор должен быть отменяем, пока прогон не начался. При
запуске из «Приложений и возможностей» никакого списка за мастером нет, поэтому там «Назад»
остаётся недоступной, а не открывает экран, которого человек не видел.

Всё вне мастеров отвечает на тот же вопрос, не задавая его. CLI и оба MCP-сервера берут язык с
этой машины, откатываются на английский там, где перевода нет, и переопределяются командой
`localai policy set --language <en|ru|system>` для всех процессов, запущенных после. Их строки
лежат парами `.resx`, а не в коде: язык добавляется файлом, а тест не пропускает язык, в котором
переведена лишь часть. Единственное исключение — абзац про проверку обновлений. Это
согласие, и оно обязано обещать одно и то же на любом языке, на котором его спрашивают, —
а этого тест на полноту проверить не может. Поэтому абзац остаётся парой констант в одном
файле, выбирается по языку, к которому пришёл процесс, и имеет собственный тест, который
не пропускает поддержанный язык, на который у него нет ответа. За языком не следует то, что читает машина: команды, имена параметров,
идентификаторы, описания MCP-инструментов и все числа, длительности и даты — они остаются
инвариантными, чтобы строка, процитированная агентом дословно, значила одно и то же независимо
от того, где её напечатали.

Тот же исполняемый файл — ещё и деинсталлятор, обновлятор и средство починки, поэтому при
запуске он спрашивает, что за прогон сейчас будет, и предлагает только то, что машина
позволяет, называя причину для остального. Обновление к тому же перестаёт переспрашивать то, что уже есть: установленные пререквизиты,
скачанные модели, прочитанную с диска политику резидентности и существующие регистрации
клиентов оно сворачивает, поэтому в панели четыре шага вместо восьми, и счётчик говорит именно
это. Правило видеопамяти и выбор моделей — одна страница, именно в таком порядке. Их было
две, и пересчёт, который вызывает смена правила — смягчение открывает больше моделей, —
приходился на страницу, которую читатель уже покинул: он выбирал модели под фильтром,
который следующая страница молча меняла. На одной странице правило стоит над своим
следствием, а строка внутри группы моделей повторяет его вместе со счётчиком, поэтому
связь видна и после того, как радиокнопки ушли вверх.

Вместе с ними сворачивается и выбор выпуска: задача уже решила, какой это выпуск, поэтому
его получение — работа, а не вопрос, и происходит оно за первой страницей, а не за кнопкой.
Страница по-прежнему называется «Проверка системы» и по-прежнему показывает,
что нашлось; на этом пути ждут на ней выпуск не меньше, чем машину. Свёрнутое возвращают две кнопки на
странице подтверждения — отдельно выпуск, отдельно настройки: это разные вопросы. То, что
подтверждение обещает сделать, оно и делает: если ничего не выбрано и выпуск не проверен, там
написано, что не будет выполнено ничего, а не описана работа, которой не случится. И каждую
настройку оно называет теми словами, какими её предлагала страница, а не идентификатором из
кода: список, который читают перед согласием, — не место для имени элемента перечисления.
Их значения всё равно попадают на страницу подтверждения — свёрнутая страница не должна
превращаться в неперечисленный эффект, — а одна кнопка там возвращает все четыре для того
прогона, где перенесённый ответ оказался не тем.

Этот ответ едет вместе с окном: заголовок называет задачу, а в панели шагов на каждой
странице стоит строка версии — `0.1.51` на компьютере, где ничего не установлено,
`0.1.50 → 0.1.51` при обновлении, `0.1.50 → 0.1.50 (repair)`, когда запрошен тот же выпуск,
что уже стоит. У строки две половины, и живут они по разным правилам. Левая — то, что было на
этом компьютере до прогона: она читается из указателя версии один раз, за первой страницей, и
больше не перечитывается никогда — установка этот указатель переписывает, поэтому более позднее
чтение отвечает уже на другой вопрос, и на финальной странице `0.1.50 → 0.1.51` превращалось в
`0.1.51 → 0.1.51 (repair)` ровно в тот момент, когда человек читает результат. Правая — то, что
этот прогон туда кладёт. Это не история, и к моменту открытия окна она известна не всегда:
выпуск разрешается за первой страницей, а запрос, оставленный на `latest`, перепроверяется ещё
раз непосредственно перед установкой — на случай, если, пока мастер стоял открытым, вышел
новый. Поэтому она меняется — `checking…`, пока опрашивают фид, `no release`, если ответ так и
не пришёл, и сам номер версии, когда он есть, — вплоть до момента, когда прогон её окончательно
определит, и дальше стоит.

Установка регистрирует себя в разделе «Приложения и
возможности», и запись оттуда запускает копию установщика, оставленную в рантайм-корне, — так
удаление доступно и спустя долгое время после того, как скачанный файл убрали. Настройки живут в собственном каталоге — `settings` внутри рантайм-корня, — а не россыпью
рядом с очередью и индексами. Раньше их отличал от всего остального список имён файлов в
матрице удаления, и список отстал: `semantic-navigation.json` — настоящая настройка, которую
матрица считала неопознанным файлом рантайма, поэтому переустановка, обещавшая сохранить
настройки, её удаляла. Каталог отстать не может: добавить настройку и сообщить о ней матрице —
одно и то же действие. Чтение откатывается на старый путь для установок, сделанных до
разделения, а следующая запись эту копию убирает — поэтому старый файл остаётся запасным
вариантом, а не вторым экземпляром, вечно хранящим устаревший ответ. Это важнее, чем кажется:
всё, что по-прежнему собирало старый путь вручную, продолжало его находить, пока рантайм читал
другой, — из-за чего установщик записывал в журнал откат для файла, которого не писал.

То, что человек выбирает для себя, а не для машины, лежит вообще вне рантайм-корня — в
`%APPDATA%\LocalAi`, который переезжает вместе с профилем и переживает удаление. Разделение
проведено по тому, к чему настройка привязана: политика резидентности — утверждение про
видеокарту этого компьютера, пределы индексации — про его память, и перенос любого из них на
другую машину был бы переносом неверного ответа.

Само удаление —
матрица, а не один молоток: три пресета поверх строк, которые меняются по одной; всё удаляемое
перечислено до начала работы; брокера просят завершиться до того, как тронут корень; каталог
ключей подписи сохраняется, пока не дано отдельное подтверждение. По ходу работы удаление
сообщает, до чего дошло, — просит брокер остановиться, переписывает конфигурации клиентов,
снимает диспетчеры хуков, удаляет файлы, завершает, — потому что одна только остановка может
занять две минуты, а полоса, не двигавшаяся две минуты, — это ровно то, из-за чего установщик
убивают на середине. Сама страница — отдельный объект, а не часть окна удаления: то, какие
галочки ставит пресет, и есть контракт между ней и планировщиком, а чистой переустановке нужна
та же страница внутри установщика, где вторая копия стала бы вторым ответом на этот вопрос.

В обоих мастерах шаг помечен пройденным потому, что на нём были, а не потому, что он левее
того места, где читатель стоит сейчас. Положение подменяло собой историю ровно до тех пор,
пока страницы нельзя было сворачивать и раскрывать не по порядку: кнопка раскрытия вставляет
три шага перед текущим и сдвигает каждое запомненное положение на другой шаг, а финальная
страница, до которой дошли, минуя предыдущие, помечает работу, которой не было. Отметка «шаг
пройден» — это утверждение о том, что произошло с компьютером, и это единственное утверждение,
в котором панель шагов не имеет права ошибиться.

Пресет «под переустановку» сохраняет регистрации клиентов и диспетчеры хуков, а не спрашивает
о них: следующая за удалением установка перезапишет все три, а вопрос, заданный дважды,
получает два несогласованных ответа. Страница подтверждения говорит об этом словами того пути,
которым сюда пришли: из чистой переустановки — что предстоящая установка их перезапишет; при
ручном выборе пресета в обычном удалении — что здесь никого не отключают и какие строки надо
отметить, чтобы это изменить. То единственное, что в промежутке действительно ломается,
названо так же: диспетчеры, оставшиеся указывать на исчезнувший launcher, — это постоянное
состояние, когда дальше ничего нет, и интервал, когда дальше идёт установка, поэтому заметка о
сохранённом говорит, что именно из двух производит этот прогон, а финальная страница перестаёт
называть остановку на этом месте бесплатной. Запись в «Приложениях и возможностях» на этом пути
не трогают по той же причине и ещё по одной: снять её и записать обратно в пределах одного
прогона — лишняя работа на хорошем пути, а на плохом удаление, запущенное из «Приложений и
возможностей», выполняется из отложенной копии установщика, поэтому её удаление достаётся
циклу повторов, который продолжает попытки ещё минуту после выхода процесса — достаточно,
чтобы снести копию, которую к тому времени записала половина установки, и оставить запись,
указывающую в никуда, без возможности удалить. К тому же запись всё это время верна: прогон
заканчивается тем, что LocalAi установлен.

Каталог версии назван по коммиту, из которого собран, поэтому один указатель не может сказать,
какой выпуск установлен. Это записывает `bin\installed-release.json` — рядом с указателем, а не
внутри него: указатель пишет launcher под compare-and-swap по его точным байтам. Запись
называет каталог, который описывает, поэтому откат, сделанный без манифеста, оставляет
заметно устаревшую запись, а не уверенно неверный ответ.

Знать о вышедшем релизе — по согласию и по умолчанию выключено. Если включить, брокер забирает
манифест последнего релиза и его подпись не чаще раза в интервал — о машине не отправляется
ничего — и верит версии только после проверки подписи. Узнанное попадает в файл состояния,
который читают `localai doctor` и `index_status`; установить что-либо можно только командой
`localai update`, и она отказывается, пока у брокера есть задачи в очереди, если не попросить
подождать. Активация останавливает всё, что работает из уходящей версии, и заново не
запускает: клиенты поднимут новую при следующем обращении к инструменту.

Каждый прогон пишет журнал своих эффектов в `%LOCALAPPDATA%\LocalAi-installer-logs` — намерение
до эффекта, исход после, — поэтому прогон, убитый посреди установки, всё равно оставляет
запись. Неудачный или отменённый прогон предлагает откат доказуемо обратимого: активации при
обновлении, политики резидентности, записи запуска Ollama и файлов конфигурации клиентов. Что
остаётся — установки winget/npm, скачанные модели, корень первой установки — названо прямо, а
не подразумевается отменённым. Прерванный прогон предлагается обратно при следующем запуске;
прогон, ещё идущий в другом окне, распознаётся по живому замку и не трогается.

### 9.1 Активация, откат и остановка

| Операция | Как устроена |
|---|---|
| Активация | Требует явно назвать заменяемый указатель — либо его контрольную сумму, либо утверждение «указателя ещё нет». Пропуск обеих гарантий считается ошибкой применения, а несовпадение — отказом |
| Откат версии | Это не «отмена», а активация ранее проверенного неизменяемого каталога: он никогда не переписывался, поэтому доступен целиком |
| Остановка | Брокера просят завершиться: запрос с его идентификатором и временем старта кладётся рядом с документом состояния, брокер замечает его на своём ежесекундном сердцебиении, перестаёт брать новую работу и доводит текущую до конца |
| Принуждение | Убивают только того, кто не ушёл к сроку. Брокер владеет устойчивой очередью и может быть в середине многоминутного вывода, поэтому уничтожение — крайняя мера, а не механизм |
| Инструменты MCP | Своего состояния не имеют и канала для просьбы тоже, а клиент перезапускает их сам, поэтому для них остановка — это просто завершение |

Запрос на остановку называет и время старта, а не только идентификатор процесса: иначе устаревший
запрос мог бы погасить здоровый брокер, унаследовавший тот же идентификатор.

### 9.2 Настройки, которые читаются на лету

Ни одна из них не требует пересборки; часть не требует и перезапуска.

| Файл | Что задаёт | Когда вступает в силу |
|---|---|---|
| Политика моделей | Требование к резидентности, удержание модели после простоя | Брокер читает при старте: уже запущенный держит прежнюю политику |
| Границы хранения | Поколения, версии, бэкапы, архив, тела ответов, телеметрия | При очередном проходе уборки |
| Профиль разбора логов | Контексты, фрагменты, перекрытие, оценка символов на токен | Перед каждым вызовом |
| Языковые серверы | Включение, исполняемые файлы, таймауты, предел размера сообщения | При следующем открытии документа |
| Внешние индексаторы | Включение, пути, аргументы, лимиты разбора | При каждой синхронизации |
| Проверка обновлений | Можно ли узнавать о новых релизах и как часто. По умолчанию выключена | Брокер читает при старте: уже запущенный держит прежнюю политику |

Мастер читает эти файлы прежде, чем предложить их, поэтому прогон, не заходивший на страницу
настройки, записывает обратно то, что на машине уже было. Если прогон всё-таки меняет настройку,
страница подтверждения говорит об этом прямо — `Update check: off (currently on - this run
changes it)`, — потому что показанное значение читается как «что будет настроено», а не как «что
будет заменено».

Испорченный или неизвестной версии файл политики **не ослабляет** проверку: применяются безопасные
значения по умолчанию. Ошибка разбора никогда не превращается в молчаливое разрешение. Проверка
обновлений — самый острый случай этого правила: нечитаемый `update-check.json` означает
*выключено*, потому что файл, который никто не может разобрать, — не согласие обращаться к сети.

## 10. Границы и ограничения

| Ограничение | Что это значит на практике |
|---|---|
| Потолок железа | Ориентир — одна видеокарта на 16 ГБ. Модель, живущая за счёт размазывания по двум картам, платит обменом через шину и на одной карте просто не запустится |
| Теги моделей обманчивы | Тег вида «8b» может означать четырёхбитный квант. Для качества нужен явный тег квантования, а проверять его следует по манифесту реестра, а не по имени |
| Смена модели эмбеддингов | Требует пересборки индекса: модель записана в заголовке, запросить индекс чужой моделью невозможно |
| Живые языковые серверы | Выключены по умолчанию, включаются отдельным файлом настроек |
| NPU не помогает | Всё идёт через Ollama, чьи backend'ы — процессор, CUDA, ROCm, Metal и Vulkan |
| Локальные модели слабее | Хороши на «перечисли» и «суммируй», ненадёжны в тонком анализе; всё, от чего зависит решение, перепроверяется |

## Приложение. Где что лежит

| Путь | Что |
|---|---|
| `bin\versions\<версия>` | Неизменяемые бинарники версии |
| `bin\launcher` | Стабильная точка входа |
| `bin\current.json` | Указатель активной версии |
| `repositories\<id>\generations` | Поколения индексов |
| `policy.json` | Резидентность моделей и удержание модели в памяти |
| `retention.json` | Границы хранения |
| `log-triage.json` | Профиль разбора логов |
| `language-servers.json` | Живые языковые серверы, по умолчанию выключены |
| `semantic-indexing.json` | Внешние индексаторы точной навигации |
| `update-check.json` | Можно ли узнавать о новых релизах и как часто. По умолчанию выключено |
| `update-state.json` | Что нашла последняя проверка; из этого файла отвечают все поверхности |
| `bin\installed-release.json` | Из какого опубликованного выпуска взят активный каталог версии |
| `telemetry\metrics` | Записи задач |
| `diagnostics.jsonl` | На чём брокер сбоил в последний раз и, если сбоило само задание, с каким текстом. По объекту JSON в строке, ограничен, одна ротация хранится |

Все пути — относительно каталога рантайма LocalAi в локальных данных приложения пользователя.
Отчёты и журналы прогонов установщика лежат рядом с этим каталогом, в `LocalAi-installer-logs`, —
намеренно вне валидируемого корня установки.
