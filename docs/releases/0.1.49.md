# LocalAi 0.1.49

[Русская версия](0.1.49.ru.md)

Two fixes and one shipped diagnostic, all descending from one community report: the
"Dll was not found." of issue #139, twice closed as not reproduced, came back from
@Platonenkov's machine with a stack trace, a two-command repro and the root cause located —
and everything in this release follows from settling it.

**This release does not rebuild anything.** Chunk boundaries, the semantic format and the
generation identity are unchanged; an existing index stays valid.

## The single-file localai.exe finds hostfxr

`MSBuildLocator.RegisterDefaults()` enumerates installed SDKs by P/Invoking into `hostfxr`.
A framework-dependent process has that module loaded before the first managed instruction;
the released `localai.exe` is a self-contained single-file publish, where the host components
are statically linked into the apphost — no `hostfxr` module exists in the process, and on a
machine where the import resolved no other way, the Roslyn phase of `localai sync` died as a
bare `DllNotFoundException` on any repository with a real project. It hid well: a repository
of loose `.cs` files skips the Roslyn phase entirely, and one whose `semantic.sidx` already
exists resumes without ever loading a solution — so a machine where sync once succeeded
looked healthy until the first non-resumable change.

A preloader now runs immediately before registration. Where `hostfxr` already resolves —
every machine that worked — nothing is loaded and nothing changes. Where it does not, the
dotnet roots are walked the way the host itself would (`DOTNET_ROOT_<ARCH>`, `DOTNET_ROOT`,
the installation owning `dotnet` on PATH, the default install location) and the newest
`host\fxr\<version>\hostfxr.dll` is loaded by full path; the Locator's import then binds to
the loaded module. Confirmed on the reporting machine: the preload line names the loaded
library, and sync completes with full C# semantics.

## The stack trace ships instead of requiring a rebuild

Locating the failure above took the reporter a local rebuild whose only change was appending
the stack. That option now ships: `LOCALAI_STACK=1` (or `true`) appends the full exception
with its stack trace under the one-line failure rendering. The default output stays a single
line — the contract from 0.1.46 that operators and hooks parse.

## The publish script accepts the prerelease versions its own pattern promises

The script's version pattern deliberately allows `0.1.49-pr189`, and the signer models a
prerelease as a first-class component — but `AssemblyVersion` and `FileVersion` are numeric
quads by definition, and deriving them as `$ReleaseVersion.0` made a suffixed version pass
validation and die half a build later as CS7034. The numeric part is now stripped once for
the properties that are numeric by meaning (`AssemblyVersion`, `FileVersion`,
`VersionPrefix`); `Version`, `InformationalVersion`, the package URI and the signer keep the
full string, so a diagnostic build labels itself as the prerelease it is instead of wearing a
plain number indistinguishable from a real release. Found by the reporter while building the
branch that fixed the failure above.

## The Russian README says what the English one says

A fidelity pass over every document pair found the damage concentrated in `README.ru.md`,
whose runtime-and-security and routing sections carried machine-translation artifacts that
inverted or lost meaning: offload rendered as disabling with cause and effect swapped,
chunking and embedding rendered as trimming and attachments, Git hook names translated word
by word, a dropped "unless" that inverted a development rule. All are restored to the English
text's meaning, and both READMEs now document `LOCALAI_STACK`.
