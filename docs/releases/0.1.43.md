# LocalAi 0.1.43

[Русская версия](0.1.43.ru.md)

A search hit is now something you can navigate from, and the declarations 0.1.42 could not cut
on get chunks of their own. This is the release where `find_references` starts working from a
`search_code` result, which was one of the reasons symbol-aware chunking was worth doing and had
quietly never been true.

**This release rebuilds every repository's index once.** Chunk boundaries are part of the
generation identity and they changed, so the first sync after installing it builds a new base
generation from scratch. Read the upgrading section before you start it.

## Navigating from a search result

A hit reports a path and a line range. The column of the identifier inside that line is nowhere
in it, so the obvious call is column zero — and column zero lands on `export`, or on an indent,
which names no symbol. Navigation then fell through to its bounded text heuristic, and asking
for references to a component came back with six matches for the word `export` in a swagger
file: correctly labelled as degraded, and completely useless.

A position that names nothing, on a line that declares exactly one thing, now resolves to that
declaration. The start line of a hit navigates as it stands. A line that declares two things —
`const a = f(), b = g()` — still returns nothing rather than guessing which was meant, and a
line holding only references is left alone, because resolving it would answer about a symbol
nobody pointed at. The change is in the resolver all four navigation tools share.

## Declarations the indexer names but reports no body for

`scip-typescript` reports no `enclosing_range` for a declaration whose initialiser is a call,
which is exactly what `export const X = memo(() => …)` is. Those declarations were dropped, so
on a React repository the component a file is named after was the one thing in it without a
chunk — 1 222 declarations across the corpus 0.1.42 was measured on.

They are cut now, on a boundary read off the file rather than guessed: a declaration runs to the
line before the next thing the indexer named. Three rules keep that honest, and each was
measured before being chosen rather than after.

A comment above a declaration documents that declaration, so it is not absorbed by whatever was
declared above it. Without that rule a one-line constant followed by a doc comment grew to seven
lines, earned a chunk it should not have had, and filed the comment explaining the next function
under the constant's name.

A declaration that ends on the line it starts on stays in the window. On that corpus 487 of the
1 222 are one-liners like `const access = 'authenticated' as const;`, and admitting them adds 438
chunks to buy 495 more source lines under a symbol — a vector per line is the same bad bargain as
a vector per DTO property.

Which bodiless definitions qualify is decided by the symbol the indexer gave them. Only SCIP
declarations with a term or type descriptor: the XAML indexer reports every `x:Key` without a
body and a resource key has no extent to infer, and `scip-typescript` reports 13 308 meta
descriptors on that corpus — one per property of every object literal — where a vector per
property is the bloat symbol-aware chunking exists to avoid.

Declarations written inside a function body still keep the window. That is a decision with a
measurement behind it, in `SymbolAwareChunker`: the indexer names them `local N` with neither a
name nor a span, the only handle on them is a hover string, and on that corpus the hover says
`function` or `class` exactly never.

## What it measures

Same repository, same commit, same twelve cases as the 0.1.42 table:

| | 0.1.41 and earlier | 0.1.42 | 0.1.43 |
|---|---:|---:|---:|
| Precision@5 | 0.116667 | 0.116667 | 0.133333 |
| Recall@10 | 0.750000 | 0.750000 | 0.750000 |
| Mean first relevant rank | 5.500000 | 4.916667 | 4.750000 |
| Response characters | 70 245 | 66 087 | 63 281 |
| TypeScript/Python hits naming a symbol | 0 of 86 | 33 of 85 | 50 of 89 |

Precision moved for the first time in this line of work, and it is one more relevant hit inside
the top five across twelve cases — a direction, not an effect size, and the notes say so because
a twelve-case corpus cannot say more. What it does measure is coverage: 56% of the hits in those
languages name a symbol rather than 39%, and the response is another 4.2% smaller.

Ranking was the obvious next suspect and it was tried and rejected. Giving a symbol chunk an RRF
bonus over a windowed one does exactly what it says — three to five window hits give way to
symbol hits — and not one of the hits it promotes is relevant. Two magnitudes, no metric moved,
responses grew about 1%. The measurement is in `docs/codesearch-evaluation.md`; the knob is not
in the code.

## Fewer minutes lost to an interrupted sync

The semantic phase runs before embedding so that a failed adapter costs minutes instead of the
whole embedding budget. It had no checkpoint of its own: the staged semantic index carried a
per-run identifier and was deleted on the way out, so every resume rebuilt a file identical to
the one it had just thrown away.

It is now named for the generation, survives that cleanup, and is deleted when the generation is
published. Matching the generation id is the whole staleness test — the id already covers the
repository, the git tree, the model and every format version — and anything unreadable is
treated as absent, because a checkpoint is an optimisation and no optimisation may fail a build.

## Smaller things you will notice

`repo status` names the repository it is answering about. A caller reaches it with a path, from
inside a worktree, or with nothing at all, and each resolves to a common directory that may not
be the one they had in mind; a bare `NOT_CONFIGURED` could not be checked against anything.

A branch whose overlay was degraded by a failed external indexer says so, naming the worktree
and the adapter. The base generation refuses to publish in that situation and a branch carries
on, which is deliberate — refusing would fail the post-commit hook on every commit until someone
repaired a Node package — but it was previously silent about it.

## Upgrading

Install with the GUI installer from this release, then run a sync per repository. The first one
rebuilds the base generation.

Budget for it. On the React repository the corpus grew again, 6 079 chunks to 6 868, because
declarations that used to share a window now have vectors of their own; the rebuild embedded all
of them in about eleven minutes while sharing the broker queue with another repository's build.
A large C# solution is on the order of an hour. `index_status` reports it as a build in progress
with a live count and an ETA, which is what it is.

Branch overlays are rebuilt on the same sync and cut on the same boundaries as the base, so a
file changed on a branch does not have a different chunk shape from the same file on the
mainline.

## Verification

The complete solution ran 1 839 tests: 1 835 passed and four skipped for platform reasons.

Among them is a corpus this repository owns. A generator writes a small front end
deterministically, 48 committed cases ask questions of it, and CI indexes that tree with the real
`scip-typescript`, cuts it with the real chunker and asserts what the chunker documents in prose:
a call-initialised declaration gets a chunk, an object literal's properties do not, a one-line
declaration stays in the window, every source line lands in exactly one chunk. No embedding model
is involved, so it runs on every pull request — and it earned its place on the first run, by
finding the comment-absorbing boundary described above.

What that corpus cannot do is grade retrieval, which was measured rather than assumed: its
hand-written cases answer at rank 1.00 every time and its templated ones at 7.15, because a
generated corpus is either unique enough that nothing can be got wrong or repetitive enough that
nothing can be told apart. Retrieval numbers still come from a real repository, measured locally,
with the provenance written down in `docs/codesearch-evaluation.md`.

Two tests now pin that chunking is deterministic — the same file cut twice, and the same
definitions arriving in a different order, produce the same chunks in the same order, embed text
included. A boundary that moved between two runs of one build would change every chunk id
downstream of it.

CI also runs on every pull request now, not only those based on `main`. A pull request based on
anything else previously showed a green tick it had never earned, because "no required run" and
"run passed" look the same in the merge box.
