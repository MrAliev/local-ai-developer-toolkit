# LocalAi 0.1.38

[Русская версия](0.1.38.ru.md)

Upgrading no longer requires shutting the runtime down by hand, and a release whose assets the
GitHub CLI refuses to download can still be installed.

## An upgrade no longer refuses the machine it is upgrading

Taking the installation layout opened every directory of it with `FILE_OPEN_IF` and asked for
`DELETE` on each. Windows refuses `DELETE` on a directory another process holds without
`FILE_SHARE_DELETE`, and the runtime root is exactly such a directory whenever the broker is
running: it is that process's working directory. The result was that installing over a machine
where LocalAi had been used stopped at the very first gate, with `check: OpenRelative` and nothing
else to act on.

The installer has always been able to clear its own way — it asks the launcher it is about to
install to stop the running tools, then replaces them. That step sat several steps past the gate
and was therefore unreachable. Now only directories the installation creates are opened with
`DELETE`, because those are the ones it deletes again when an installation fails before it
commits; directories that were already there are opened without it. With the gate passable, the
existing stop-and-retry does the rest: closing clients or stopping the broker before an upgrade is
no longer part of the procedure.

A refusal from a directory open now names the directory and the NTSTATUS, so a layout that really
is unavailable says which one and why instead of naming only the check that ran.

## Releases the CLI cannot download

`gh release download` fails on some releases even when the machine is signed in and the asset
exists. When it does, the installer now resolves the release through GraphQL, reads the asset list
over the REST API, and downloads the asset by its numeric id. Asset bytes are streamed from the
process straight into the target file rather than through a text reader, which corrupts arbitrary
byte sequences, and the downloaded file is accepted only when its length matches the size GitHub
reports. Both the original failure and the fallback's own failure are reported together, so a
genuine authentication problem still reads as one.

## Upgrading

Install with the GUI installer from this release. It stops the broker and the running MCP servers
itself, replaces them, and activates the new version; nothing has to be closed beforehand. Clients
reconnect on their next request. An installer executable downloaded before this release still
carries the old gate — download this one.

## Verification

The complete solution passed 1,775 tests with four platform-dependent skips.

The refused-upgrade path is pinned by tests that hold a directory exactly the way Windows holds a
running process's working directory: the layout is accepted while that handle is open, a directory
that is genuinely unavailable is still refused by path and NTSTATUS, and a refused installation
still removes the scaffold it created.
