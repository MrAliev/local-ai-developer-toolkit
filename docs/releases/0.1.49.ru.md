# LocalAi 0.1.49

[English version](0.1.49.md)

Два исправления и одна диагностика в поставке — всё выросло из одного отчёта сообщества:
«Dll was not found.» из issue #139, дважды закрытого как невоспроизводимое, вернулось с
машины @Platonenkov со стек-трейсом, двухкомандным репро и найденной первопричиной — и всё
в этом релизе следует из её устранения.

**Сам по себе этот релиз ничего не пересобирает.** Границы чанков, семантический формат и
идентичность поколения не менялись; существующий индекс остаётся действительным.

## Single-file localai.exe находит hostfxr

`MSBuildLocator.RegisterDefaults()` перечисляет установленные SDK через P/Invoke в
`hostfxr`. В framework-dependent процессе этот модуль загружен ещё до первой управляемой
инструкции; выпускаемый `localai.exe` — self-contained single-file публикация, где
хост-компоненты статически влинкованы в apphost: модуля `hostfxr` в процессе нет, и на
машине, где импорт не разрешался никаким другим способом, Roslyn-фаза `localai sync`
умирала голым `DllNotFoundException` на любом репозитории с настоящим проектом. Пряталось
это хорошо: репозиторий из голых `.cs` пропускает Roslyn-фазу целиком, а репозиторий с уже
существующим `semantic.sidx` возобновляется, не загружая решение вовсе, — поэтому машина,
где sync однажды прошёл, выглядела здоровой до первого невозобновляемого изменения.

Теперь непосредственно перед регистрацией работает прелоадер. Там, где `hostfxr` и так
разрешается — на каждой машине, которая работала, — ничего не загружается и ничего не
меняется. Там, где нет, — корни dotnet обходятся так, как это делал бы сам хост
(`DOTNET_ROOT_<ARCH>`, `DOTNET_ROOT`, установка, которой принадлежит `dotnet` в PATH,
каталог установки по умолчанию), и новейший `host\fxr\<версия>\hostfxr.dll` загружается по
полному пути; импорт Locator привязывается к загруженному модулю. Подтверждено на машине
из отчёта: строка прелоада называет загруженную библиотеку, sync завершается с полной
семантикой C#.

## Стек в поставке, а не в локальной пересборке

Чтобы найти описанный выше сбой, автору отчёта пришлось локально пересобрать CLI ради
единственного изменения — дописанного стека. Теперь эта возможность в поставке:
`LOCALAI_STACK=1` (или `true`) добавляет полное исключение со стеком под однострочный вывод
сбоя. По умолчанию вывод остаётся одной строкой — контракт из 0.1.46, который разбирают
операторы и хуки.

## Publish-скрипт принимает prerelease-версии, которые обещает его собственный шаблон

Шаблон версии в скрипте намеренно допускает `0.1.49-pr189`, а signer моделирует prerelease
как полноправный компонент — но `AssemblyVersion` и `FileVersion` по определению числовые
четвёрки, и вывод их как `$ReleaseVersion.0` позволял версии с суффиксом пройти валидацию и
умереть посреди сборки с CS7034. Числовая часть теперь выделяется один раз для свойств,
числовых по смыслу (`AssemblyVersion`, `FileVersion`, `VersionPrefix`); `Version`,
`InformationalVersion`, URI пакета и signer сохраняют полную строку, поэтому диагностическая
сборка называет себя тем prerelease, которым является, а не носит гладкий номер,
неотличимый от настоящего релиза. Найдено автором отчёта при сборке ветки с исправлением
сбоя выше.

## Русский README говорит то же, что английский

Проход по каждой паре документов на верность перевода показал, что повреждения
сосредоточены в `README.ru.md`: разделы про рантайм-безопасность и маршрутизацию несли
следы машинного перевода, искажавшие или терявшие смысл, — offload превратился в
«отключение» с перевёрнутой причинностью, нарезка на чанки и эмбеддинг — в «обрезку и
вложения», имена Git-хуков были переведены пословно, а выпавшее «не» инвертировало одно из
правил разработки. Всё восстановлено по смыслу английского текста, и оба README теперь
описывают `LOCALAI_STACK`.
