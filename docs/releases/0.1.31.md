# LocalAi 0.1.31

[Русская версия](0.1.31.ru.md)

Three reporting defects found while releasing and installing 0.1.29 and 0.1.30. None of them
corrupts data; each one made the installer describe itself wrongly, which is how two of them
survived being looked at directly.

## Keep latest meaning latest

Choosing "latest" and installing gave 0.1.29 while 0.1.30 was already published.

Nothing was cached, and the feed resolves the tag correctly — the request itself was being
overwritten. `SelectResolvedRelease` wrote the resolved tag back into `ReleaseVersion`, so the
first time the page checked a release, "latest" became "0.1.29". Every later check then asked
GitHub for that exact tag and got exactly what it asked for. The field displayed a specific
version, which looks like a deliberate choice rather than an answer that had replaced the
question.

The request and the answer are now separate fields. A request left at "latest" is also
re-resolved immediately before the download, because a wizard can sit on the confirmation step
across a release; a tag named explicitly is left alone.

## Say a release is already installed before installing it

The wizard never said that the release it was about to install was the one already active. The
installer handles it correctly — it reports `AlreadyInstalled` and changes nothing — but
afterwards, in a line of the finish log. A run that was never going to change anything looked
exactly like one that did until it was over.

That is what the previous defect looked like from the outside: a "latest" resolving to the
installed version ran to completion, and the only evidence was that `bin\current.json` had not
moved.

## Record why a publish failed

`Invoke-SafePublish` kept only the exit code of `dotnet publish`. When publishing went to the
wrong tree it reported seven successful publishes and then failed on the missing artifacts,
with nothing recorded to explain either. The output is now captured, echoed, and its tail
carried into the retry warning and the final exception.
