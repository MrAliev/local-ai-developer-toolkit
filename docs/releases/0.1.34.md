# LocalAi 0.1.34

[Русская версия](0.1.34.ru.md)

A feature that could not work, a test that could not fail, and the review that found both.

## A language server can be told how to start

`typescript-language-server` locates tsserver by looking for a TypeScript package in the
workspace. A workspace that does not carry its own gets `Could not find a valid TypeScript
installation`, and the server exits. Live TypeScript navigation was therefore unavailable in every
repository without a local `node_modules/typescript`, and nothing the operator could configure
would change it.

TypeScript 7 widens the gap rather than closing it: it no longer ships `lib/tsserver.js` at all, so
a machine with a perfectly current global TypeScript still has nothing this server can drive.

The way to say where a working tsserver lives is the LSP `initializationOptions` member, and the
client never sent it — the word appeared nowhere in the source tree, and the policy had nowhere to
put it. Both carry it now, and `language-servers.json` accepts it per language:

```json
"typescript": {
  "Enabled": true,
  "Executable": "typescript-language-server",
  "Arguments": ["--stdio"],
  "InitializationOptions": { "tsserver": { "path": "…/node_modules/typescript/lib/tsserver.js" } }
}
```

Two details are load-bearing. The member is **absent rather than null** when nothing is configured,
because a server that reads it without checking gets a null where it expects an object. And the
field is optional rather than a schema bump, so an installation configured before 0.1.34 keeps
loading — bumping the version would invalidate every existing file and silently replace it with the
disabled defaults.

Never inferred. LocalAi will not go looking for a tsserver to nominate on the operator's behalf:
navigating with a different TypeScript than the project builds with produces wrong answers that
look like right ones.

## The fixture that reported a product defect it had caused

The real TypeScript fixture asked only whether the server binary existed, then built its workspace
in a temporary directory with no TypeScript in it. On a machine with the server installed it ran,
failed at initialize, and reported a product failure that was really a missing prerequisite. On a
machine without the server it skipped. Neither outcome said that live TypeScript navigation had
never once been exercised.

It now resolves a tsserver the server can actually drive and names it explicitly. The skip guard is
deliberately narrow: it fires only when a prerequisite is provably absent. A server that is
present, with a tsserver that is present, that then fails to initialize, keeps the test red.
Turning a failed initialize into a skip is the shape of the 0.1.31 and 0.1.32 defects, where opt-in
fixtures that never ran read as coverage.

Both real LSP fixtures, TypeScript and pyright, now execute.

## A test that could not fail

`InvalidOrUnknownConfigurationFallsBackToDisabledDefaults` hand-wrote a camelCase document. The
language-server store configures no naming policy, so its members are spelled the way the CLR
spells them, and every member of that document was unmapped. The test passed because nothing bound
at all — it would have passed with the unknown-member guard deleted, which makes it worse than
absent, because the coverage report counted it.

It is built from a real serialized policy now, and it was verified the way the old one never was:
with `UnmappedMemberHandling` relaxed to `Skip` the test fails, and it passes again when the guard
is restored. The old name claimed two behaviours and exercised neither, so it is two tests.

## One definition of the runtime root

Five places built `%LOCALAPPDATA%\LocalAi` out of the same two parts: the CLI three times, the
broker client as its fallback, and the launcher's process controller. Each was correct, and each
was a separate answer to "which installation" — the question 0.1.33's injectable runtime root
exists to give exactly one answer to. They defer to that one definition now. The path is unchanged,
so this removes the chance of drift rather than any drift that had happened.

## Verification

The full suite across all nine projects is **1678 passed, 4 skipped, 0 failed**, up from 1665
passed with 1 failing in 0.1.33.

The four remaining skips are symbolic-link and reparse-point tests that need Windows Developer
Mode. They guard against reads escaping the repository through a link, and they skip on a provably
absent capability rather than on a failure — but they are worth running on a machine where that
capability exists.
