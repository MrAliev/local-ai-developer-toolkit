# Канонический CRLF в индексе и точный статус overlay

[English version](2026-07-28-canonical-crlf-overlay-status-design.md)

## Контекст

LocalAi строит неизменяемую базу CodeSearch из Git snapshot и точный overlay для каждого
неосновного или грязного worktree. В Windows snapshot обычно содержит LF, а checkout — CRLF или
смешанные окончания строк. Из-за побайтового hash неизменённые файлы дублируются в overlay.
Устаревшее представление статуса также считает совпадение пути достаточным, чтобы не использовать
overlay, даже когда текущий worktree имеет dirty-content identity.

## Цели

- Сделать identity индекса независимой от физических окончаний строк.
- Использовать Windows CRLF как каноническое представление индексируемого текста в памяти.
- Применять одно представление к hash, чанкам, embeddings и dirty-content identity.
- Никогда не переписывать файлы репозитория.
- Определять необходимость точного overlay по Git tree и dirty-content identity.
- Принудительно построить новое базовое поколение, чтобы старое и новое представления не
  смешивались.

## Дизайн

### Канонический текст

Единый helper нормализации CodeSearch преобразует `CRLF`, одиночный `CR` и одиночный `LF` в
`CRLF`. Он работает со строками, уже прочитанными из индексируемых текстовых файлов.

IndexBuilder использует канонический текст для:

- SHA-256 hash каждого файла;
- входа chunker;
- входа embeddings, созданного из этих чанков.

DirtyCorpusPolicy использует тот же канонический текст при расчёте hash рабочего содержимого.
Пути и границы файлов остаются частью dirty-content digest, поэтому одинаковое содержимое разных
файлов не создаёт коллизий.

Helper никогда не записывает канонический текст обратно на диск. Фрагменты результатов поиска
по-прежнему читаются из текущего worktree и сохраняют его физические окончания строк. Номера строк
после нормализации не меняются.

### Совместимость поколений

Версия нормализации CodeSearch в `GenerationIdentity` увеличивается. Из-за этого меняется ID
поколения, и LocalAi строит новую базу и точные overlays. Существующие поколения остаются
неизменяемыми и не переиспользуются с новой нормализацией.

### Необходимость overlay и status

Для индексов с generation worktree требует overlay, если выполняется хотя бы одно условие:

- его Git tree отличается от Git tree базы;
- присутствует dirty-content hash.

`SearchService.Status` явно возвращает это решение. CLI сначала отображает существующий точный
overlay и только затем рассматривает legacy-проверку пути базы. Если overlay необходим, но
отсутствует, status показывает `NOT BUILT`. Для чистого worktree на tree базы status сообщает, что
overlay не нужен.

Legacy-индексы без generation ID сохраняют существующее поведение на основе пути.

## Обработка ошибок

- При ошибке чтения сохраняется текущее поведение: файл пропускается в этом запуске индексации.
- Отсутствующий или несовпадающий exact overlay по-прежнему блокирует поиск вместо молчаливого
  смешивания устаревших данных.
- Нормализация детерминирована и не зависит от конфигурации Git или культуры хоста.

## Тестирование

- LF-база и эквивалентный CRLF-worktree создают пустой overlay.
- Входы CR, LF, CRLF и mixed дают одинаковый канонический hash и текст чанков.
- Реальное изменение текста по-прежнему создаёт запись overlay.
- Dirty content при том же commit/tree требует overlay.
- Чистый worktree на tree базы не требует overlay.
- Status показывает существующий exact overlay даже при совпадении путей базы и worktree.
- Полные build и test LocalAi остаются чистыми.
- Индекс Jira перестраивается и проверяется exact overlay и семантическим запросом.

## Вне области задачи

- Перезапись файлов репозитория или изменение `.gitattributes`.
- Изменение Git `core.autocrlf`.
- Установка hooks, замена глобальных бинарников, commit или push.
