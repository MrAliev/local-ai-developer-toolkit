# Дизайн совместимости протокола и сборки broker

**Issue:** [#6](https://github.com/MrAliev/local-ai-developer-toolkit/issues/6)

**Дата:** 2026-07-31

**Статус:** согласован

## Цель

Позволить установленному broker и development-клиенту совместно использовать
единственный общесистемный broker, если они реализуют один явный compatibility
contract, даже когда их сборки находятся по разным путям. Действительно
несовместимые host должны отклоняться без ослабления singleton, устойчивого FIFO,
runtime ACL, безопасной активации launcher и гарантий full-VRAM/zero-offload.

## Границы

Изменение ограничено обнаружением broker, классификацией совместимости,
координацией запуска, диагностикой и контрактом состояния host. Оно не меняет
планирование очереди, маршрутизацию моделей, транспорт Ollama, политику
резидентности, переводов или владения версиями launcher.

Windows-установщик реализуется в отдельном issue, branch и PR.

## Контракт совместимости

`LocalAi.Contracts` владеет одним неизменяемым значением совместимости broker:

- `ProtocolVersion` — машиночитаемая версия протокола broker/client;
- `BuildCompatibilityId` — стабильный идентификатор семейства совместимых сборок.

Build compatibility ID не является commit SHA, версией assembly или путём в
файловой системе. Совместимые сборки сохраняют одно значение. Оно меняется
только при несовместимом изменении runtime semantics, даже если форма протокола
остаётся читаемой.

`BrokerProcessState` переходит на schema 3 и публикует:

- идентичность процесса и heartbeat;
- версию протокола;
- build compatibility ID;
- путь к assembly broker.

Путь остаётся диагностическими данными и доступен `LocalAiProcessController`
для определения принадлежности broker активированной версии. Он больше не
участвует в проверке совместимости.

## Классификация состояния клиентом

Перед решением о запуске клиент классифицирует состояние host:

- `CompatibleHealthy` — свежий heartbeat, совпадающая идентичность процесса и
  совместимые protocol/build значения. Host переиспользуется.
- `IncompatibleHealthy` — живой host с неподдерживаемой schema, protocol или
  build family. Немедленная ошибка с ожидаемыми и фактическими значениями.
- `AbsentOrStale` — состояние отсутствует, повреждено, устарело или потеряло
  владельца. Клиент входит в синхронизированный запуск.
- `StartingOrLockOwned` — другой процесс запускается либо дочерний процесс
  завершился с кодом 0, вероятно проиграв `broker.lock`, пока активный владелец
  публикует состояние. Клиент продолжает ограниченное ожидание без повторного
  запуска.
- `FailedStart` — дочерний процесс завершился с ненулевым кодом до появления
  совместимого состояния. Диагностика содержит exit code и последнее
  наблюдавшееся состояние.
- `TimedOut` — истёк ограниченный срок. Сообщается последняя классификация и
  результат запуска вместо общего readiness timeout.

Повреждённое, некорректное или недоступное состояние запуска остаётся
наблюдением отсутствующего/недоступного состояния и может завершиться
типизированной ошибкой `broker_start_timeout`; само по себе оно не становится
`FailedStart`. Ненулевой exit code дочернего процесса приводит к
`broker_start_failed`, а код 0 наблюдается как вероятное наличие владельца lock.

Живой legacy broker со schema 2 считается несовместимым, а не отсутствующим.
Это предотвращает бессмысленный запуск второго процесса за занятым lock.

## Координация запуска

Существующий именованный semaphore, зависящий от runtime root, остаётся
клиентской защитой от двойного запуска. Эксклюзивный `broker.lock` остаётся
примитивом общесистемного владения broker.

Единый монотонный бюджет запуска начинается до получения semaphore. Клиент
проверяет его после начального чтения состояния непосредственно перед созданием
процесса, сразу после возврата из синхронного системного вызова `Process.Start`
и перед каждой задержкой опроса. Сам `Process.Start` нельзя прервать; cancellation
и оставшийся бюджет проверяются сразу после его возврата.

Абстракция запуска возвращает наблюдаемую попытку, а не только PID. Клиент
может определить, работает ли дочерний процесс, и получить exit code после его
завершения. Запуск остаётся отделённым и не наследует стандартные потоки.

После попытки запуска каждое состояние проходит общий классификатор. Проигрыш
`broker.lock` успешен только при совместимом активном владельце. Несовместимый
владелец приводит к немедленной compatibility error.

## Инварианты launcher и безопасности

- `LocalAiProcessController` продолжает использовать диагностический путь для
  остановки или блокировки активации процессов, принадлежащих version directory.
- `VersionLease`, activation mutex, атомарная замена `current.json` и проверка
  активной версии не меняются.
- `RuntimeAcl.Ensure` по-прежнему выполняется до захвата broker lock и публикации
  состояния host.
- Дополнительный broker и прямой доступ к Ollama не появляются.
- Семантика FIFO и проверки full-VRAM/zero-offload не меняются.

## Модель ошибок

Ошибки совместимости и запуска получают типизированные коды для CLI/MCP:

- `broker_incompatible`;
- `broker_start_failed`;
- `broker_start_timeout`.

Сообщения содержат безопасные compatibility values, сведения о процессе и exit
code при наличии, а также последнюю классификацию. Содержимое заданий,
credentials и чужие command lines не раскрываются.

## TDD и проверка

Каждый тест сначала создаётся и наблюдается падающим. Обязательное покрытие:

- совместимые protocol/build ID при разных физических путях DLL;
- несовместимые ID при одинаковом пути;
- живой legacy schema, устаревший, отсутствующий и повреждённый `host.json`;
- конкурентные совместимые клиенты запускают ровно один процесс;
- дочерний процесс проигрывает `broker.lock` совместимому владельцу;
- дочерний процесс проигрывает lock несовместимому владельцу;
- ранний выход процесса и диагностика exit code;
- bounded timeout с последним наблюдавшимся состоянием;
- владение версией launcher по assembly path после исключения пути из
  compatibility check;
- неизменность activation lease, singleton, FIFO, ACL, full-VRAM и zero-offload.

Release-проверка:

```powershell
dotnet test LocalAi.slnx -c Release --nologo
git diff --check
git status --short
```

Работа поставляется одним feature branch и одним PR для issue #6.
